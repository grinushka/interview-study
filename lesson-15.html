Архитектура и принципы

SOLID: все пять принципов

SOLID помогает обсуждать, как код меняется и как его части зависят друг от друга. Принципы не требуют превращать каждый React-компонент в класс. Их смысл проявляется, когда новое требование заставляет менять несвязанные участки или когда реализацию невозможно заменить без неожиданных нарушений поведения.

Как это работает — по шагам

  1. S: выделяй связную ответственность. Если экран одновременно рисует UI, выбирает transport и знает детали хранения, разные причины изменения оказываются в одном месте.
  2. O и L: оставляй нужные точки расширения и соблюдай контракт замены. Новая реализация должна подходить потребителю по поведению, а не только по совпадающим именам методов.
  3. I: давай потребителю небольшой нужный интерфейс. Компоненту аватара не требуется весь административный API пользователя.
  4. D: высокоуровневый сценарий обращается к подходящей абстракции, а конкретный адаптер реализует её. Это позволяет заменить источник данных без переписывания сценария.

Разберём на примере

Форма получает функцию saveProfile, а не сама импортирует конкретный SDK во всех обработчиках. Для теста можно передать подмену, для другого backend — адаптер. Но если в проекте нет реальной вариативности, десяток абстрактных фабрик может ухудшить простоту: SOLID нужно сопоставлять с KISS/YAGNI.

Термины и элементы темы
S — Single Responsibility
Одна связная ответственность / причина изменения. Отделить отображение от сложной работы с транспортом.
O — Open/Closed
Расширять поведение через устойчивую точку расширения; например composable children вместо растущего switch по всем типам кнопок.
L — Liskov Substitution
Реализация должна сохранять обещанный контракт. Замена не должна неожиданно усиливать требования или нарушать ожидаемое поведение.
I — Interface Segregation
Небольшие интерфейсы под потребителей. Компоненту не нужен весь огромный user store ради имени.
D — Dependency Inversion
Высокоуровневая логика зависит от абстракции, а не конкретного HTTP-клиента. Передать функцию загрузки через интерфейс/параметр.

Коротко для собеседования

Расшифруй все пять принципов и связывай каждый с проблемой изменения или зависимости. Принцип полезен, когда объясняет компромисс, а не только украшает архитектуру.

KISS, DRY и YAGNI

Эти принципы ограничивают разные виды сложности. KISS обращает внимание на понятность решения, DRY — на дублирование знания, YAGNI — на ненужные предполагаемые возможности. Они не означают «всегда меньше строк» или «никогда не готовить удобные границы для изменений».

Как это работает — по шагам

  1. KISS: предпочти решение, которое проще понять и сопровождать при текущих требованиях. Иногда явные несколько строк проще хитрой универсальной функции.
  2. DRY: одно бизнес-правило лучше иметь в одном надёжном месте. Два похожих фрагмента с разными причинами изменения могут быть разным знанием.
  3. YAGNI: не реализуй заранее многопользовательскую систему plugins, если есть одна конкретная потребность. Проверяемость и понятность нужного кода не считаются лишней функциональностью.
  4. При конфликте ищи фактическую стоимость. Абстракция уменьшила повторение, но потребовала десяти flags? Возможно, сходство было внешним и общий компонент теперь слишком сложен.

Разберём на примере

Две формы выглядят одинаково, но одна — банковская заявка, другая — поиск. Общий компонент с множеством условий может связать независимые изменения. Если же в двух местах скопирована одна формула расчёта комиссии, это одно знание и его расхождение уже опасно.

Термины и элементы темы
KISS — Keep It Simple
Выбирать понятную структуру без лишних уровней; простота оценивается по пониманию и сопровождению, не только числу строк.
DRY — Don’t Repeat Yourself
Не дублировать знание и правила. Внешне похожие строки с разными причинами изменения не всегда стоит объединять.
YAGNI — You Aren’t Gonna Need It
Не строить предполагаемые возможности без текущей потребности. Нужные тестируемость и качество не считаются лишней функциональностью.

Коротко для собеседования

KISS — понятная сложность, DRY — единый источник знания, YAGNI — отсутствие преждевременных возможностей. Применять их нужно по смыслу, а не по числу строк.

YAGNI добавлен как дополнительная тема автора обратной связи, а не как исходный вопрос интервьюера.

Паттерны: учебный набор

Паттерн — название повторяемого способа решения определённой проблемы. Он полезен для разговора о структуре и компромиссах: «у нас Adapter, чтобы изолировать внешнее API» содержательнее, чем «мы сделали ещё один класс». Но название не делает любую дополнительную прослойку необходимой.

Как это работает — по шагам

  1. Observer описывает подписку на изменения; Strategy — заменяемый алгоритм; Adapter — перевод одного интерфейса в другой. У каждого своя исходная проблема.
  2. Factory концентрирует создание подходящего экземпляра. Command представляет действие как отдельное значение/объект, чтобы хранить, ставить в очередь или проектировать отмену.
  3. Во frontend многие паттерны удобно выразить функциями и композициями. Strategy может быть просто переданной функцией сортировки.
  4. Рассказ о применении должен назвать исходную задачу, выбранную границу и цену: новый уровень косвенности, lifecycle подписок или правила совместимости.

Разберём на примере

Сервис возвращает user_name, а UI ожидает name. Adapter переводит внешний ответ во внутреннюю модель, чтобы все компоненты не знали чужой формат. Если завтра transport изменится, меняется адаптер. Для одного поля в одном месте отдельная сложная иерархия может быть излишней.

Термины и элементы темы
Observer
Подписчики реагируют на события/изменения. Browser listeners и store subscriptions; нужны unsubscribe и контроль жизненного цикла.
Strategy
Взаимозаменяемый алгоритм за одним контрактом, например разные правила сортировки/валидации.
Adapter
Привести внешнее API к контракту приложения, изолировать различия.
Factory
Сосредоточить создание объекта/клиента, когда варианты зависят от конфигурации.
Command
Описать действие как значение/объект для очереди, истории или undo; обратимость нужно проектировать.
Composition / compound components
Собирать UI из частей; совместное состояние может передаваться через Context. HOC и custom hooks — варианты повторного использования поведения.

Коротко для собеседования

Знай задачу, структуру и ограничение каждого паттерна учебного набора. На собесе лучше один настоящий разбор, чем список названий без примеров.

Границы приложения и системное проектирование

Архитектура frontend — не только названия папок. Она определяет, какие части отвечают за пользовательские сценарии, какие контракты их связывают и что произойдёт при изменениях или сбоях. Начинать проектирование полезно с требований, иначе легко выбрать технологию для ещё не сформулированной проблемы.

Как это работает — по шагам

  1. Выясни ключевые сценарии и ограничения: кто пользователи, какой объём данных, нужна ли доступность без сети, как быстро должен реагировать интерфейс.
  2. Выдели компоненты ответственности: UI, state, получение данных, маршруты, интеграции. Определи, какие детали каждая часть скрывает.
  3. Опиши передаваемые данные и интерфейсы. Для поиска важны query, filters, pagination, cancellation и состояния результата, а не только компонент SearchBox.
  4. После базового пути обсуди сбои, безопасность, accessibility и performance. RADIO помогает держать этот разговор в понятном порядке.

Разберём на примере

Поиск с быстрым вводом требует учитывать ответы, пришедшие не по порядку. Один запрос на каждую букву может перегружать систему. При обсуждении решения нужны debounce или cancellation по условиям, связь URL с фильтрами, empty/error/loading states и способ продолжения списка.

Термины и элементы темы
Модули / MVC
Модуль скрывает детали за понятным интерфейсом. MVC разделяет model, view и controller; React сам по себе не задаёт полную архитектуру приложения.
Monorepo / multirepo
Способ хранения исходников, не способ исполнения. Monorepo упрощает согласованные изменения; нужны граф задач и ownership.
Микрофронтенды
Независимые части UI могут иметь собственные команды и deployment. Цена: интеграция, общий UX, зависимости, маршрутизация и observability.
RADIO
Requirements → Architecture → Data model → Interface definition → Optimizations. Обсудить accessibility, security, performance, cache и failure states.

Коротко для собеседования

Архитектура следует требованиям и явным контрактам. Monorepo — организация исходников; микрофронтенды — границы частей приложения и команд; это не одно и то же.

Module Federation

Обычная npm-зависимость чаще попадает в приложение во время сборки. Module Federation позволяет сборкам делиться модулями во время работы: host может загрузить компонент из отдельно выпущенного remote. Это поддерживает независимые поставки, но переносит часть рисков совместимости на runtime.

Как это работает — по шагам

  1. Remote объявляет, какие модули доступны снаружи. Host знает, как найти remote и какой модуль запросить.
  2. Runtime загружает нужный код и организует взаимодействие с общими зависимостями. Shared-конфигурация помогает согласовать React и другие библиотеки.
  3. Одна общая копия React важна для согласованной работы hooks, но singleton сам не превращает несовместимые версии в совместимые. Нужны правила версий и интеграционные проверки.
  4. Remote может быть недоступен в момент открытия страницы. Область ошибки, fallback и возможность продолжить работу проектируются как часть пользовательского сценария.

Разберём на примере

Команда корзины выпускает remote Cart отдельно от каталога-host. Каталог не обязан пересобираться после каждого совместимого изменения корзины. Но если новый remote перестал соблюдать props-контракт или его сервер не отвечает, host должен обработать это контролируемо.

Термины и элементы темы
Host / remote
Host потребляет exposed modules remote; remote entry/runtime описывает загрузку.
Shared
Разделять совместимые зависимости, часто React как singleton. Выбор версий зависит от конфигурации и порядка инициализации; singleton не гарантирует совместимость.
Надёжность
Загрузка remote может упасть. Нужны fallback, Error Boundary, timeout/повтор и совместимый контракт.
Build-time / runtime
npm-пакет обычно попадает в сборку host; remote может обновляться независимо, что требует контроля совместимости.

Коротко для собеседования

Module Federation даёт runtime-интеграцию сборок, а не автоматическую архитектурную независимость. Контракты, shared dependencies и обработка отказов остаются обязанностью приложения.

Модульность, Atomic Design и FSD

Atomic Design, FSD и группировка по типам файлов предлагают разные способы видеть структуру кода. Они отвечают на разные вопросы: из каких UI-частей собирается экран, как изолировать бизнес-функции, где искать одинаковые технические артефакты. Полезно сравнивать их по реальным изменениям, а не по красоте дерева папок.

Как это работает — по шагам

  1. Atomic Design описывает композицию: простые элементы образуют более крупные группы, затем участки экрана и страницы. Это особенно полезно для языка дизайн-системы.
  2. Группировка components/hooks/store объединяет файлы по техническому виду. На маленьком проекте удобно; большая feature может оказаться разбросанной по нескольким каталогам.
  3. FSD выделяет layers и slices вокруг областей ответственности и пользовательских сценариев. Public API и правила импортов должны помогать контролировать связанность.
  4. Модульность означает скрытие деталей за контрактом, а не только наличие папки modules. Ни один набор названий сам по себе не предотвращает взаимные зависимости.

Разберём на примере

Новый сценарий «применить купон» затрагивает UI, проверку и state. Если всё разложено только по типам файлов, изменения приходится собирать по всему проекту. Feature-модуль помогает держать связанное рядом. Внутри его UI при этом можно использовать компоненты, построенные по Atomic Design.

Термины и элементы темы
Модульность
Модуль скрывает внутреннее устройство. Группировка по типам файлов — только один вариант; feature-модули тоже модульны.
Atomic Design
Atoms → molecules → organisms → templates → pages. Полезная модель композиции дизайн-системы, но не обязательные папки.
Feature-Sliced Design
Слои и slices по доменам/сценариям: shared, entities, features, widgets, pages, app. Контролировать public API и направление зависимостей.

Коротко для собеседования

Подходы могут сочетаться. Выбирай структуру, которая делает обычные изменения локальными и зависимости понятными; проверяй это на сценариях, а не на названиях слоёв.
