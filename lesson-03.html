Безопасность и хранение

TLS и сертификат

При обычной передаче через сеть между браузером и сервером есть посредники. Нужно защититься от чтения и незаметного изменения данных, а также убедиться, что соединение установлено с нужным сервером. TLS решает эти задачи для канала связи. Сертификат участвует прежде всего в проверке личности сервера.

Как это работает — по шагам

  1. Браузер получает сертификат и проверяет, соответствует ли он запрошенному имени, действует ли по времени и связан ли с доверенной цепочкой.
  2. В процессе handshake стороны согласовывают параметры защищённого обмена и получают ключи для дальнейшей передачи.
  3. Защищённые сообщения шифруются и проверяются на целостность. Посредник не должен суметь незаметно заменить содержимое.
  4. После расшифровки приложение всё ещё обязано проверять входные данные и права. Если сервер сам выдаёт чужой заказ, TLS защищённо доставит именно этот ошибочный ответ.

Разберём на примере

Когда открываешь https://shop.example, важна проверка сертификата именно для shop.example. Сам факт шифрования с неизвестным собеседником не доказывает, что это магазин. Поэтому игнорирование предупреждения о сертификате разрушает существенную часть защиты.

Термины и элементы темы
Конфиденциальность
Перехватчик не читает содержимое запросов и ответов.
Целостность
Изменения защищённых данных обнаруживаются.
Аутентичность сервера
Проверяются имя хоста, срок действия и цепочка доверия сертификата.

Коротко для собеседования

TLS защищает транспорт: конфиденциальность, целостность и аутентичность сервера. Он не заменяет авторизацию, защиту от XSS или корректность бизнес-логики.

Уточнение к Notion: историческое название «SSL-сертификат» обычно относится к сертификату для современного TLS.

Origin, CORS и OPTIONS

Страница, открытая на одном origin, не должна автоматически читать приватные ответы любого другого сайта. Иначе вредоносная страница могла бы действовать как читатель данных из твоих других сессий. CORS позволяет серверу явно разрешить определённым origins чтение ответов из браузерного JavaScript.

Как это работает — по шагам

  1. Origin состоит из схемы, host и порта. https://app.example и https://api.example — разные origins, даже если принадлежат одному продукту.
  2. Для запроса, требующего preflight, браузер сначала спрашивает сервер через OPTIONS: разрешены ли нужные origin, метод и заголовки.
  3. Если предварительная проверка успешна, браузер отправляет основной запрос. Затем он проверяет CORS-заголовки основного ответа, прежде чем отдать его скрипту.
  4. Некоторые запросы уходят без preflight. Отсутствие разрешения может помешать чтению ответа, но сервер уже мог выполнить действие. Поэтому CORS не является защитой от CSRF.

Разберём на примере

Frontend на localhost:5173 запрашивает API на localhost:3000. В curl ответ виден, а fetch не даёт прочитать его: curl не применяет браузерную same-origin policy. Править нужно разрешения API или схему размещения, а не добавлять Access-Control-Allow-Origin в клиентский запрос.

Термины и элементы темы
Простой запрос
Может уйти без preflight. Без разрешающих заголовков браузер не предоставит ответ скрипту, хотя сервер мог выполнить действие.
Preflight
Для некоторых методов, headers и content types браузер сначала отправляет OPTIONS с Origin и Access-Control-Request-*.
Разрешение
Сервер отвечает Access-Control-Allow-Origin, при необходимости Allow-Methods/Allow-Headers. Для credentials нужен Allow-Credentials и конкретный origin вместо *.
Граница защиты
curl не применяет браузерный CORS. Защита от CSRF и проверки доступа на сервере нужны отдельно.

Коротко для собеседования

CORS контролирует доступ браузерного кода к cross-origin ответу. Разрешение сообщает сервер, применяет браузер; проверка прав пользователя — отдельная задача.

Уточнение к Notion: браузер не всегда блокирует саму отправку cross-origin запроса; часто он блокирует доступ к ответу.

Cookies: назначение и атрибуты

Cookie — значение, которое браузер хранит для сайта и при подходящих условиях автоматически добавляет к запросу. Сервер часто использует его как идентификатор сессии: по этому значению узнаёт, к какому вошедшему пользователю относится запрос. Автоматическая отправка отличает cookies от localStorage.

Как это работает — по шагам

  1. Сервер задаёт cookie через Set-Cookie. Вместе со значением он указывает область отправки, срок жизни и ограничения доступа.
  2. Перед запросом браузер сопоставляет URL и контекст с правилами cookie. Domain и Path ограничивают подходящие адреса; Secure и SameSite добавляют другие условия.
  3. HttpOnly запрещает чтение через document.cookie. Браузер всё равно может отправлять такую cookie в запросах: именно это нужно для многих сессий.
  4. Срок жизни определяется Expires/Max-Age либо сессией браузера. Завершение сессии и восстановление вкладок зависят от поведения браузера.

Разберём на примере

В session=abc не обязательно лежат имя и права. Это может быть случайный ID, по которому сервер находит сессию. HttpOnly мешает украсть ID простым чтением JavaScript, Secure ограничивает транспорт, SameSite сокращает часть cross-site отправок. Эти атрибуты дополняют друг друга.

Термины и элементы темы
Expires / Max-Age
Дата истечения / время жизни в секундах. При наличии обоих Max-Age имеет приоритет.
Domain / Path
Область отправки по домену и пути. Path не является защитной границей доступа к данным.
Secure
Ограничить отправку защищённым соединением; существуют специальные localhost-исключения.
HttpOnly
Не давать JavaScript читать cookie через document.cookie. Это не предотвращает все последствия XSS.
SameSite
Strict/Lax/None ограничивают cross-site отправку. SameSite=None требует Secure; cross-site и cross-origin — разные понятия.
Session / persistent
Без Expires/Max-Age cookie сессионная, но восстановление сессии браузера может её восстановить. Типичный лимит одной cookie около 4 KiB.

Коротко для собеседования

Cookie связывает браузерный запрос с сохранённым значением. Каждый атрибут отвечает на свой вопрос: куда, как долго, по какому соединению и при каком контексте отправлять.

Хранилища браузера

Выбор хранилища начинается с потребности: данные нужны одной вкладке или всем, должны переживать перезапуск или только reload, являются настройками или большими структурированными объектами. «Сохранить в браузере» не означает автоматически отправить данные на сервер или гарантировать вечное хранение.

Как это работает — по шагам

  1. localStorage хранит строковые пары и доступен синхронно. Для объекта нужен явный способ сериализации. Маленькие настройки — подходящий случай; большие операции могут мешать основному потоку.
  2. sessionStorage имеет похожий API, но отдельное состояние для вкладки. Это помогает хранить текущий шаг мастера, не меняя шаг в соседней вкладке.
  3. IndexedDB хранит структурированные данные асинхронно и поддерживает транзакции. Cache API работает с объектами запросов и ответов, например для offline-ресурсов.
  4. Cookies нужны, когда важна автоматическая отправка по HTTP и связанные атрибуты. Остальные хранилища сами ничего не прикладывают к каждому запросу.

Разберём на примере

Тему интерфейса можно сохранить в localStorage, временный шаг формы — в sessionStorage, большой offline-набор документов — в IndexedDB, ответы для offline-страницы — в Cache API. Сессионный идентификатор часто хранится в подходящей защищённой cookie. Квоты и ошибки доступа нужно учитывать в каждом варианте.

Термины и элементы темы
Cookies
Небольшие значения, автоматическая отправка подходящим запросам, атрибуты безопасности.
localStorage
Синхронные строковые пары ключ–значение, общие для origin и сохраняемые между сессиями. Квота ограничена, доступ может быть запрещён.
sessionStorage
Строковые пары для origin и конкретной вкладки. Переживает reload; новая вкладка может получить исходную копию, но далее хранит её отдельно.
IndexedDB
Асинхронное транзакционное хранилище структурированных данных и Blob. Подходит для offline и больших наборов; квота и возможное вытеснение зависят от браузера.
Cache API
Хранилище пар Request/Response с явным управлением. Используется для offline, не равно автоматическому HTTP-кэшу.

Коротко для собеседования

Cookie подходит для автоматически передаваемого session ID с выбранной моделью защиты. localStorage — для небольших сохраняемых настроек, sessionStorage — для черновика конкретной вкладки. IndexedDB хранит структурированные offline-данные и Blob асинхронно, Cache API — пары Request/Response. У всех вариантов учитывать область, квоту и возможную недоступность; наличие записи не гарантирует вечное хранение.

Уточнение к Notion: квоты не универсальны; IndexedDB доступен и workers, а не только коду страницы.

Аутентификация и авторизация

После входа приложение решает две разные задачи. Аутентификация устанавливает, кто обращается. Авторизация проверяет, разрешено ли этому пользователю действие над конкретным ресурсом. Разница становится очевидной, когда два вошедших пользователя имеют разные права или владеют разными документами.

Как это работает — по шагам

  1. При аутентификации пользователь подтверждает личность. После этого клиент обычно получает сессию или токен, который предъявляет в следующих запросах.
  2. На каждом защищённом запросе сервер проверяет credentials и их актуальность. Наличие строки в localStorage не доказывает серверу личность само по себе.
  3. Затем проверяется разрешение: можно ли читать этот заказ или удалять именно этот документ. Проверки только роли иногда недостаточно — важны владелец и состояние ресурса.
  4. UI может скрывать недоступные действия ради удобства, но пользователь способен отправить запрос вручную. Реальная граница доступа остаётся на сервере.

Разберём на примере

Пользователь А вошёл в систему и имеет право редактировать свои документы. Он меняет URL запроса с /documents/10 на /documents/11, принадлежащий Б. Проверка «пользователь вошёл» пройдёт; нужна отдельная проверка права на документ 11.

Термины и элементы темы
Сессия
Браузер хранит идентификатор сессии, сервер связывает его с пользователем. Cookie часто HttpOnly, Secure и с подходящим SameSite.
Bearer token
Тот, кто предъявил токен, получает соответствующий доступ. Нужны срок жизни, отзыв/обновление и защита хранения; JWT — формат, а не синоним авторизации.
Проверка прав
Каждый защищённый запрос проверяется сервером для действия и ресурса. CASL может описывать правила в UI, но не заменяет сервер.
OAuth/OIDC
OAuth делегирует доступ; OpenID Connect добавляет идентификацию. Popup требует проверки origin/state и безопасного обмена результатом.

Коротко для собеседования

Проверка должна отказать на сервере до удаления: текущий пользователь должен иметь право удалить именно этот ресурс. Скрытая кнопка — только удобство интерфейса. Дополнительно нужны корректная аутентификация и защита выбранного способа передачи credentials.

Уязвимости и защита

Похожие названия защит легко спутать, если учить их отдельно от механизма атаки. Сначала нужно понять, что злоумышленник заставляет сделать систему: выполнить чужой код, отправить действие с чужими credentials или раскрыть ресурс без разрешения. После этого становится понятно, где должна стоять защита.

Как это работает — по шагам

  1. При XSS недоверенные данные превращаются в исполняемый код страницы. Для обычного текста использовать безопасный текстовый вывод; для разрешённого HTML нужна корректная sanitization.
  2. При CSRF атакующая страница заставляет браузер инициировать запрос с автоматически приложенными credentials. Важно ограничивать такие отправки и проверять происхождение/токен действия.
  3. При broken access control сервер разрешает не то действие или не тот ресурс. Это устраняется серверными проверками, а не только скрытием UI.
  4. CSP ограничивает исполнение/загрузку контента, HTTPS защищает канал, мониторинг помогает обнаружить происшествие. Ни одна мера не устраняет все классы атак.

Разберём на примере

Если имя пользователя вставить через textContent, строка с HTML останется текстом. Если вставить её как недоверенный HTML, она может изменить документ и стать источником XSS. HttpOnly усложнит чтение cookie, но исполняемый код всё ещё может отправлять действия от лица пользователя.

Термины и элементы темы
HTML injection / XSS
Вставка недоверенного HTML опасна; использовать контекстное escaping, безопасные DOM API, sanitization для разрешённого HTML. React экранирует текст, но dangerouslySetInnerHTML требует защиты.
CSP
Политика источников и выполнения контента; nonce/hash и строгая script-src уменьшают риск исполнения чужого кода. Не замена исправлению XSS.
CSRF
Чужой сайт инициирует действие с автоматически прикладываемыми credentials. Защита: SameSite, CSRF-токены, проверка Origin; не выполнять изменения через GET.
Broken access control
Проверять права на сервере, включая доступ к конкретному объекту. Скрытая кнопка и случайный ID не являются защитой.
Компоненты и мониторинг
Обновлять уязвимые зависимости, ограничивать права, логировать подозрительную активность без секретов и персональных данных.

Коротко для собеседования

Выбирай защиту по механизму угрозы. XSS, CSRF и нарушение доступа требуют разных основных мер и нескольких дополнительных уровней.
