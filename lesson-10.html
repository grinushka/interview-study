React: приложение

Controlled и uncontrolled компоненты

У input есть собственное состояние в DOM: пользователь может печатать, даже если React ещё ничего о введённом тексте не сохранил. Controlled подход делает React state источником значения поля. Uncontrolled оставляет текущее значение в DOM и читает его, когда оно понадобится.

Как это работает — по шагам

  1. В controlled input prop value задаёт показанное значение. onChange должен сохранить новый ввод в state, чтобы следующий render вернул обновлённое value.
  2. Если value есть, но state не обновляется, поле будет возвращаться к заданному значению. Пользовательский ввод не становится источником истины автоматически.
  3. В uncontrolled input defaultValue задаёт начальное значение. Дальнейший ввод хранится DOM; при submit его можно прочитать через FormData или ref.
  4. Выбор определяется нужной связью с UI: немедленная зависимая валидация, вычисление других полей, интеграция и частота обновлений. Не стоит случайно менять режим одного поля в середине его жизни.

Разберём на примере

Для калькулятора цены, который пересчитывается при каждом символе, controlled поле удобно. Для простой формы с чтением данных только при отправке может хватить uncontrolled. defaultValue не означает «поддерживать это значение вечно»: это начальная настройка, а не постоянное управление.

Термины и элементы темы
Controlled
value/checked + onChange; удобно для взаимозависимых полей и отображения состояния.
Uncontrolled
defaultValue/defaultChecked задают начальное значение. Подходит для простых форм и интеграций.
Границы
Не переключать один input между controlled и uncontrolled в течение жизни. Файловый input требует чтения FileList.

Коротко для собеседования

Controlled: React state → value → событие → новый state. Uncontrolled: DOM хранит ввод, React задаёт стартовые значения и читает результат по необходимости.

HOC, custom hooks и React Router

HOC, custom hook и Router часто появляются в одном проекте, но решают разные задачи. HOC оборачивает компонент и добавляет поведение. Custom hook делится логикой внутри компонентов. Router согласует URL с тем, какой UI показывается. Совпадение способов реализации не делает эти понятия взаимозаменяемыми.

Как это работает — по шагам

  1. HOC получает компонент и возвращает другой компонент. Он может добавить props или проверки, но создаёт дополнительную границу, важную для refs, отладки и композиции.
  2. Custom hook вызывается внутри компонента и возвращает данные или действия. Он явно показывает, какая логика подключена; отдельные вызовы не становятся одним общим state автоматически.
  3. Router сопоставляет путь, параметры и вложенные маршруты. Клиентская навигация обновляет историю и UI без обязательной полной загрузки документа.
  4. При прямом открытии /orders/7 сервер или hosting должны уметь отдать входную страницу или соответствующий SSR-ответ. Router в браузере не может исправить серверный 404, возникший до загрузки приложения.

Разберём на примере

withPermissions(Page) может обернуть страницу проверкой. usePermissions() даёт компоненту данные для собственной композиции. Маршрут /admin выбирает страницу по адресу. Это три независимых решения. SPA описывает способ навигации, но не исключает серверный HTML при первом открытии.

Термины и элементы темы
HOC
withPermissions(Component) может добавить поведение. Учитывать передачу props, refs и вложенность wrappers.
Custom hook
usePermissions() возвращает данные/действия и явно используется компонентом. Вызовы custom hook не делят state автоматически.
Router
Сопоставляет URL маршрутам и вложенным layouts; клиентская навигация использует History API. Современный React Router не сводится к HOC.
SPA
Документ остаётся, приложение меняет UI при навигации; сервер должен поддерживать прямые URL. SPA может использовать SSR при первой загрузке.
Шаблоны и компоненты
Handlebars подставляет данные в текстовый HTML-шаблон. React-компонент объединяет описание UI с композиционной моделью, state и обновлениями; оба подхода могут генерировать HTML на сервере.

Коротко для собеседования

HOC меняет компонент через обёртку, hook повторно использует логику, Router связывает URL и UI. Современный React Router не следует объяснять как «просто HOC».

Suspense и lazy loading

Suspense показывает запасной UI, когда часть дерева ещё не готова к render из-за поддерживаемого асинхронного источника. Важно отличать эту приостановку от ситуации, когда компонент уже отрендерил пустой список и только потом начал fetch в эффекте. React не превращает любое ожидание в Suspense автоматически.

Как это работает — по шагам

  1. React.lazy получает функцию динамического импорта. При попытке отрендерить ещё не загруженный компонент React может приостановить эту часть дерева.
  2. Ближайшая подходящая Suspense boundary показывает fallback, пока нужный ресурс не готов. После готовности React может отрендерить содержимое.
  3. Для данных нужна интеграция, поддерживающая Suspense: framework, соответствующий источник или API use с подходящим Promise. Обычное isLoading в state — отдельный подход.
  4. Ошибка загрузки не равна ожиданию. Для ошибок render/lazy нужна Error Boundary; иначе один fallback ожидания не объяснит пользователю сбой.

Разберём на примере

Редактор текста используется редко, поэтому его код загружается через lazy при открытии. Suspense показывает skeleton. Если скачивание bundle завершилось ошибкой, нужен экран ошибки с retry, а не бесконечный skeleton. Список, загружаемый через useEffect, сам по себе не начнёт suspend.

Термины и элементы темы
React.lazy
Загружает код компонента через dynamic import и работает с Suspense.
Данные
Suspense работает с поддерживаемыми framework/data sources или use(Promise). Обычный fetch внутри useEffect сам по себе не активирует fallback.
Ошибки
Suspense отвечает за ожидание, Error Boundary — за ошибки render/lazy. Нужны оба сценария для remote-модуля.

Коротко для собеседования

Suspense отвечает за поддерживаемое ожидание при render, lazy — за загрузку кода, Error Boundary — за ошибку. Это связанные, но разные механизмы.

Версии React и миграции

На вопрос о версиях интервьюер может проверять и знания, и реальный опыт. Полезно прямо разделять то, что ты использовала, и то, что изучила. Рассказ о миграции оценивается не по названию версии, а по пониманию совместимости, изменившегося поведения и способа проверить результат.

Как это работает — по шагам

  1. Начни с конкретных проектов и версий, которые помнишь. Если точный minor неизвестен, не придумывай его; объясни используемые возможности и где проверила бы package.json/lockfile.
  2. Новые возможности связывай с задачами. Например, transition помогает приоритетам UI; optimistic update временно показывает предполагаемый результат действия.
  3. Для миграции сначала читается upgrade guide, затем проверяются зависимости, React DOM API, типы, сборка и критичные сценарии.
  4. Обновление библиотеки и рефакторинг всего приложения лучше не смешивать без необходимости: иначе сложнее связать ошибку с причиной. Результат проверяется тестами и наблюдаемым поведением.

Разберём на примере

Если миграцию ты не проводила, допустимый ответ: «В проекте работала с такой версией; самостоятельно переход не делала. Сначала проверила бы зависимости и guide, затем прогнала критичные сценарии и посмотрела изменения эффектов/форм». Это честнее и полезнее выдуманной истории.

Термины и элементы темы
React 18
createRoot, automatic batching, transitions и concurrent foundations; оценить StrictMode-проверки.
React 19
Actions, useActionState, useOptimistic, use для ресурсов/context; ref как prop для function components. useFormStatus находится в react-dom.
React 19.2
Activity сохраняет state скрытого дерева с остановкой effects; useEffectEvent отделяет нереактивную логику эффекта; Performance Tracks помогают профилированию.
React 19.3
Стабильные ViewTransition и Fragment Refs; browser() и интеграция Trusted Types. Обзор сверён 10 ноября 2026; доступность проверять для проекта.
Миграция
Зафиксировать исходную/целевую версии, проверить зависимости и removed APIs, провести typecheck и тесты ключевых сценариев, замерить поведение. Для 18 → 19 официальный guide рекомендует сначала 18.3 с предупреждениями о несовместимостях.
Рассказ
Контекст проекта → причина → изменения → проблемы → проверка результата. Если миграций не было, честно объяснить план действий.

Коротко для собеседования

Опыт и осведомлённость — разные части ответа. В миграции важно объяснить исходное состояние, причину, риски, проверку и результат.

История из опыта

История из опыта нужна, чтобы показать ход решения задачи. Без контекста список технологий мало что доказывает: одинаковый инструмент можно применить случайно или обоснованно. Хорошая история позволяет понять, что происходило, что сделала именно ты и как узнала, что стало лучше.

Как это работает — по шагам

  1. Кратко задай контекст: продукт, пользователи, твоя ответственность. Затем назови конкретную проблему, которую можно наблюдать.
  2. Объясни выбор: какие варианты были, что ограничивало сроки или архитектуру и почему выбранное решение подходило.
  3. Раздели командный результат и свой вклад. Расскажи о действиях, отладке и проверке без преувеличения роли.
  4. Заверши известным итогом и выводом. Если точных процентов нет, подойдут проверяемые качественные результаты: исчез баг, прошёл сценарий, уменьшилось число повторных запросов.

Разберём на примере

Можно рассказать, как поле поиска вызывало лишние обновления, как ты нашла причину в Profiler и переместила state. Но эту историю стоит использовать только если такой эпизод действительно был. Сам шаблон не является готовой биографией.

Термины и элементы темы
Контекст и задача
Какой продукт, твоя роль, ограничения и наблюдаемая проблема.
Выбор решения
Какие альтернативы рассматривала и почему выбрала конкретную.
Действия и проверка
Что сделала лично, как проверила корректность и результат.
Итог и вывод
Назови известный результат без придуманных процентов; что бы изменила сейчас.

Коротко для собеседования

Контекст → задача → альтернативы → действия → проверка → итог. Конкретика важнее красивых, но непроверенных чисел.
