TypeScript, type/interface и union

TypeScript проверяет допустимые операции над значениями до запуска программы. Он помогает заметить несоответствие контракту: например, функция ожидает ID, а получает весь объект. Но тип не сопровождает JSON как надёжная печать: после получения внешних данных их фактическую форму всё ещё нужно проверять во время исполнения.

Как это работает — по шагам

  1. Объектный тип описывает доступные свойства и их типы. И interface, и type могут задавать такой контракт.
  2. Interface удобно расширять через extends; одноимённые declarations могут объединяться. Type alias также описывает unions, tuples и другие конструкции, которые не являются одним объектным интерфейсом.
  3. Union A | B означает одно из допустимых значений, а не объект со всеми полями сразу. Чтобы обратиться к полю только одного варианта, нужно сузить тип.
  4. Intersection A & B требует выполнения обоих контрактов. Это не просто текстовое объединение: несовместимые требования могут сделать часть типа невозможной.

Разберём на примере

Результат запроса может быть {status:"ok", data:User} или {status:"error", message:string}. Тип результата удобно выразить union. После проверки status === "ok" компилятор разрешит data. Без проверки доступ к data был бы небезопасным для error-варианта.

Термины и элементы темы
interface
Описывает объектный контракт, поддерживает extends и declaration merging.
type
Alias для объекта, union, tuple и других типов; использует intersections, не поддерживает declaration merging как interface.
Union
A | B допускает значения одного из вариантов; для специфичных полей нужен narrowing. Intersection A & B требует совместить требования.
Цена TS
Полезен для рефакторинга и IDE, но требует настройки, времени проверки и поддержки типов. Не гарантирует отсутствие runtime-ошибок.

Коротко по теме

Type и interface часто взаимозаменяемы для объектов, но имеют разные возможности. Типы помогают статически рассуждать о значениях; внешние данные требуют runtime-валидации.

TypeScript: everyday types

never и полнота обработки

never означает, что допустимого значения в этой точке не осталось. Это полезно после разбора всех вариантов union: если ещё один вариант появился, компилятор может показать место, которое забыли обновить. Не нужно понимать never как пустую строку или отсутствие возвращаемого значения — это другой смысл.

Как это работает — по шагам

  1. Union задаёт набор возможностей. В каждой ветке проверки компилятор исключает несовместимые варианты.
  2. Если после switch не осталось вариантов, оставшееся значение можно проверить как never. Любой забытый вариант сделает такое присваивание ошибкой.
  3. Функция с never не возвращает управление нормальным возвратом: например, всегда бросает исключение. void допускает нормальное завершение без полезного результата.
  4. В conditional types never удобно удаляет неподходящие варианты: при включении в union он не добавляет новых значений.

Разберём на примере

Сегодня Status состоит из loading и done, и оба обработаны. Завтра добавили error. Проверка const unreachable: never = status в default ветке покажет ошибку: теперь там возможна строка error. Без неё ветка могла бы молча вернуть общий fallback.

type Status = "loading" | "done";
function label(status: Status): string {
  switch (status) {
    case "loading": return "Загрузка";
    case "done": return "Готово";
    default: {
      const unreachable: never = status;
      return unreachable;
    }
  }
}
  1. Каждый case исключает вариант из оставшихся возможностей.
  2. При текущем union default недостижим по типам.
  3. Если добавить новый статус без нового case, status в default уже не never и присваивание не пройдёт проверку.
Термины и элементы темы
Функция
Функция с явным возвратом never должна бросить ошибку или не завершаться; void означает отсутствие используемого результата.
Exhaustiveness
В default ветке discriminated union присвоение значения переменной never выявит забытый вариант.
Union
T | never эквивалентен T. В conditional types never часто удаляет неподходящие варианты.

Коротко по теме

never выражает невозможность значения. Основное прикладное применение — исчерпывающая обработка вариантов и фильтрация типов.

TypeScript: narrowing

Аннотация, as и satisfies

Аннотация, assertion и satisfies внешне стоят рядом со значением, но сообщают компилятору разные вещи. Аннотация задаёт тип переменной. Assertion просит рассматривать выражение как выбранный тип. satisfies проверяет контракт, не заменяя всю конкретику выражения широким объявленным типом. Ни один из них не проверяет содержимое сетевого ответа во время выполнения.

Как это работает — по шагам

  1. С : Type значение проверяется на совместимость, а переменная получает объявленный контракт. Некоторые детали конкретного инициализатора могут стать недоступны через более широкий тип.
  2. С as Type разработчик берёт на себя утверждение. Если фактические данные ему не соответствуют, выполнение не исправится: возможна обычная runtime-ошибка.
  3. С satisfies можно обнаружить неверные ключи или значения конфигурации и при этом сохранить полезные различия между её конкретными полями.
  4. as const сохраняет литеральную конкретику и readonly на уровне типа literal expression. Это не вызов Object.freeze; contextual typing при satisfies также может влиять на inference.

Разберём на примере

В palette поле green действительно является строкой, а red — RGB tuple. Аннотация Record<..., string | RGB> заставит рассматривать каждое поле через union. satisfies проверяет общий контракт, но позволяет сохранить green как строку. Для JSON неизвестного происхождения вместо as нужен настоящий разбор/валидатор.

type Color = "red" | "green";
type RGB = [number, number, number];
const palette = {
  red: [255, 0, 0],
  green: "#00ff00"
} satisfies Record<Color, string | RGB>;
palette.green.toUpperCase();
  1. Record требует ключи red и green и допускает строку или RGB для каждого значения.
  2. satisfies проверяет, что объект укладывается в этот контракт.
  3. Конкретное green остаётся строкой; вызов строкового метода допустим без проверки RGB.
Термины и элементы темы
: Type
Задаёт объявленный тип переменной и проверяет совместимость; может скрыть конкретные свойства выведенного типа за более широким контрактом.
as Type
Утверждение разработчика о типе; не runtime-cast. Может скрыть ошибку; двойное as unknown as особенно легко обходит проверку.
satisfies Type
Проверяет совместимость выражения с контрактом, сохраняя полезную конкретику результирующего типа. Контекстная типизация при этом может влиять на inference.
as const
Уточняет литералы и readonly для literal expression. Можно сочетать с satisfies; это не Object.freeze и не глубокая runtime-заморозка.

Коротко по теме

Аннотация задаёт тип; as утверждает его; satisfies проверяет совместимость с сохранением конкретики. Это compile-time инструменты, а не преобразование или проверка внешних данных.

Narrowing и Type Guards

Narrowing означает уточнение набора возможных типов на основании кода. Если значение могло быть строкой или числом, после typeof === "string" компилятор знает, что в этой ветке работают строковые операции. Важно, чтобы проверка действительно подтверждала нужное свойство, а не только выглядела похожей.

Как это работает — по шагам

  1. Встроенные проверки дают компилятору информацию: typeof, instanceof, in, равенство литералам, проверки null и другие конструкции control flow.
  2. Ранний return тоже уточняет оставшуюся ветку. Если функция завершилась для null, после проверки этот вариант больше не нужен.
  3. Discriminated union использует общее поле с literal-значением. Проверка kind выбирает вариант вместе с его остальными полями.
  4. Пользовательский predicate x is User объявляет результат проверки. Компилятор доверяет контракту такой функции, поэтому её реализация должна действительно проверять данные.

Разберём на примере

Для number | undefined проверка if (value) исключит не только undefined, но и допустимый 0. Если 0 нужен, проверяй value !== undefined. Аналогично typeof x === "object" не исключает null: это отдельная проверка, особенно перед чтением свойства.

Термины и элементы темы
typeof
Проверяет примитивные категории; typeof null === "object", поэтому null проверять отдельно.
in / instanceof
in проверяет наличие свойства; instanceof — связь с prototype конструктора. Для Array использовать Array.isArray.
Equality и truthiness
=== и !==, проверка null/undefined, ранний return. Truthiness исключает также 0, "" и false, что может быть нежелательно.
Discriminated union
Общее literal-поле kind позволяет выбрать вариант и проверить исчерпывающий switch.
Predicate / assertion function
isUser(x): x is User или asserts x is User. Реализация должна реально проверять контракт; ошибочный predicate может обмануть компилятор.

Коротко по теме

Сужение типов следует реальному потоку управления. Выбирай проверку, которая исключает только ненужные значения и доказывает именно требуемый контракт.

Utility Types: явный учебный набор

Utility Types помогают выразить производный тип без ручного копирования всех его частей. Например, форма редактирования может работать с частью полей User, а обработчик — с типом результата существующей функции. Это преобразования описаний типов: объект с лишними полями в runtime от одного Omit не изменится.

Как это работает — по шагам

  1. Раздели утилиты по задачам. Partial/Required/Readonly меняют модификаторы свойств. Pick/Omit выбирают поля объектного контракта.
  2. Record строит тип объекта по набору ключей. Exclude/Extract фильтруют варианты union, а NonNullable исключает null и undefined.
  3. Parameters и ReturnType извлекают части function type. Awaited моделирует раскрытие результата, которое делает await, включая вложенные promise-like значения.
  4. Многие объектные утилиты работают на один уровень. Readonly<User> не делает автоматически readonly все вложенные объекты; Partial<User> не делает каждое поле глубоко optional.

Разберём на примере

У User есть id, name и email. Pick<User, "name" | "email"> задаёт форму двух полей. Partial от этого типа описывает patch, в котором любое из двух полей может отсутствовать. Но данные перед отправкой всё равно нужно собрать: тип не удаляет id из существующего объекта.

Термины и элементы темы
Partial<T>
Делает собственные свойства T optional на один уровень.
Required<T>
Делает свойства обязательными на один уровень.
Readonly<T>
Запрещает присвоение свойств через этот тип на один уровень; не freeze.
Pick<T, K>
Оставляет выбранные ключи объекта.
Omit<T, K>
Исключает выбранные ключи объекта.
Record<K, V>
Объект с ключами K и значениями V.
Exclude<T, U>
Удаляет из union T варианты, присваиваемые U.
Extract<T, U>
Оставляет из union T варианты, присваиваемые U.
NonNullable<T>
Убирает null и undefined.
Parameters<F>
Tuple параметров функции.
ReturnType<F>
Тип результата функции.
Awaited<T>
Рекурсивно раскрывает promise-like результат как await.

Коротко по теме

Partial, Required и Readonly меняют модификаторы свойств; Pick и Omit выбирают ключи объекта; Record строит объект по набору ключей. Exclude и Extract фильтруют union, NonNullable исключает null/undefined. Parameters и ReturnType извлекают части типа функции, Awaited моделирует результат ожидания. Все они преобразуют типы, а не реальные значения.

TypeScript: Utility Types

Omit и Exclude

Путаница возникает из-за общего слова «исключить». У Omit единица исключения — ключ объекта. У Exclude — целый вариант union, который можно присвоить исключаемому типу. Они смотрят на разные уровни структуры, поэтому заменить один другим по похожему названию нельзя.

Как это работает — по шагам

  1. Omit<User, "id"> строит объектный тип без ключа id. Остальные выбранные свойства сохраняют свои типы.
  2. Exclude<Status, "draft"> проходит по вариантам union Status и убирает те, которые присваиваемы "draft".
  3. Его модель — T extends U ? never : T, распределённая по каждому варианту T. never затем исчезает из итогового union.
  4. Если вариантом union является целый объект, Exclude сравнивает этот вариант целиком. Он не заходит внутрь и не вырезает поле. Обычный Omit над union тоже требует осторожности с variant-specific полями.

Разберём на примере

Для {id:number; name:string} исключение поля id делает Omit. Для "draft" | "sent" | "failed" исключение draft делает Exclude. Запись Exclude<User, "id"> не удалит User.id: весь объект User не является строковым литералом "id".

type User = { id: number; name: string };
type PublicUser = Omit<User, "id">; // { name: string }
type Status = "draft" | "sent" | "failed";
type Visible = Exclude<Status, "draft" | "failed">; // "sent"
  1. Omit получает объект и имя его ключа.
  2. Exclude получает union и тип исключаемых вариантов.
  3. Каждый вариант draft, sent, failed проверяется отдельно; остаётся только sent.
Термины и элементы темы
Omit
Omit<{id:number; name:string}, "id"> даёт {name:string}. Реальный объект при этом не изменяется.
Exclude
Exclude<"draft" | "sent" | "failed", "draft" | "failed"> даёт "sent".
Распределение
Для Exclude<T,U> каждый вариант T проверяется отдельно: T extends U ? never : T. Обычный Omit над union не обязан сохранить все variant-specific поля.

Коротко по теме

Omit фильтрует ключи объектного типа. Exclude фильтрует члены union по assignability. Это compile-time преобразования, не операции с реальным объектом.

Generics и variance

Generic нужен, когда функция или контейнер сохраняет связь типов. Если положили User, хочется получить User, а не неизвестный общий объект. Variance отвечает на следующий вопрос: можно ли заменить контейнер или функцию одного типа похожим контейнером другого, если сами типы связаны наследованием/совместимостью?

Как это работает — по шагам

  1. Представь Animal и более конкретный Dog. Производитель, возвращающий Dog, подходит там, где требуется Animal: каждый полученный Dog действительно Animal. Это ковариантное направление результата.
  2. Потребитель, умеющий обработать любого Animal, подходит для Dog. Но обработчик только Dog не обязан уметь работать с кошкой. Поэтому входные параметры требуют противоположного, контравариантного рассуждения.
  3. Если структура и читает, и записывает T, безопасная замена может потребовать invariance: нельзя ни читать слишком общий результат, ни записывать неподходящий объект.
  4. TypeScript имеет прагматические исключения, в частности для method parameters. Поэтому в ответе важно различать общую модель и реальные правила strictFunctionTypes.

Разберём на примере

Функция (animal: Animal) => void безопасна для места, которое передаст Dog: она обрабатывает всех животных. Функция (dog: Dog) => void опасна для места, которое может передать любой Animal: внутри она может требовать dog.bark(). Название «контравариантность» описывает именно это направление совместимости.

Термины и элементы темы
Generic constraint
T extends {id:string} ограничивает допустимый T, но сохраняет его конкретику. Это не то же самое, что заменить T широким базовым типом.
Covariance
Производитель результата Dog может использоваться там, где нужен результат Animal.
Contravariance
Обработчик любого Animal можно использовать там, где передают Dog; обратное опасно. Проверка зависит от strictFunctionTypes и формы объявления.
Invariance / bivariance
Чтение и запись T могут требовать invariance. Некоторые method parameters допускают bivariance для совместимости; это компромисс soundness.

Коротко по теме

Generics сохраняют связь типов. Variance объясняет направление безопасной подстановки: выход обычно ковариантен, вход — контравариантен, сочетание чтения и записи может требовать инвариантности.
