От URL до страницы

От адреса до первого изображения страницы

Представь, что открываешь страницу магазина. Браузеру сначала нужно получить её содержимое, а потом превратить его в изображение. Адрес в строке — ещё не адрес конкретного компьютера: доменное имя нужно связать с IP. Полученный HTML тоже не готовая картинка: это текст с описанием структуры и ссылками на другие ресурсы.

Как это работает — по шагам

  1. Браузер разбирает адрес: каким протоколом пользоваться, к какому host обращаться и какой ресурс запрашивать. Если подходящий ответ уже доступен локально, часть сетевой работы не нужна.
  2. Если потребуется сеть и IP ещё неизвестен, DNS помогает найти адрес сервера. Затем браузер создаёт или переиспользует соединение. При HTTPS защищённый канал устанавливается с проверкой сертификата.
  3. По соединению уходит HTTP-запрос. Сервер возвращает статус, заголовки и тело. Тело HTML может поступать частями: браузер начинает разбирать его, не ожидая последнего байта.
  4. В HTML находятся ссылки на CSS, JS и изображения. Их загрузка и обработка влияют на то, когда появятся содержимое и интерактивность. Первое изображение страницы и завершение всех загрузок — разные моменты.

Разберём на примере

При первом посещении магазина могут понадобиться DNS, новое соединение и загрузка CSS. При следующем переходе на этом же сайте соединение уже открыто, а CSS лежит в кэше. Поэтому нельзя заучивать маршрут как обязательную одинаковую цепочку для каждого запроса.

Термины и элементы темы
URL и локальный ответ
Разобрать схему, host, порт, путь и query. Управляющий Service Worker может обработать запрос; HTTP-кэш может дать свежий ответ или потребовать проверки.
DNS
Если адрес ещё неизвестен и нужен сетевой запрос, получить IP по имени. Кэши сокращают эту работу.
Соединение
Для HTTPS поверх HTTP/1.1 или HTTP/2 используются TCP и TLS. Уже открытое соединение можно переиспользовать; HTTP/3 использует QUIC поверх UDP.
Запрос и ответ
Метод, URL и заголовки описывают запрос; статус, заголовки и тело — ответ. HTML может поступать частями.
Парсинг и отображение
Парсить HTML, находить CSS/JS/изображения, строить DOM/CSSOM, вычислять стили, layout, paint и compositing.

Коротко по теме

От URL до страницы есть две большие части: получение ресурсов и их отображение. Кэши и переиспользование соединений сокращают первую; парсинг, стили, layout и paint выполняют вторую.

Уточнение к Notion: TLS нужен в объяснении HTTPS; TCP не является транспортом HTTP/3. Service Worker, HTTP-кэш и DNS — не одна обязательная линейная очередь проверок.

Фазы рендеринга страницы

HTML говорит, какие элементы существуют, CSS — как они должны выглядеть. Для экрана этого недостаточно: браузеру нужно вычислить конкретные размеры, координаты и изображение каждого элемента. Названия стадий полезны для объяснения того, почему одно изменение интерфейса обходится дороже другого.

Как это работает — по шагам

  1. DOM — дерево элементов документа. CSSOM представляет правила CSS. На их основе браузер определяет итоговые стили: например, какая именно ширина применяется к карточке.
  2. Layout вычисляет геометрию: координаты и размеры блоков. Если карточка стала выше, может потребоваться передвинуть всё, что находится под ней.
  3. Paint подготавливает визуальное содержимое: текст, фоны, границы. Затем части изображения могут быть собраны из слоёв на стадии compositing.
  4. При обновлении браузер старается повторить только нужную работу. Изменение геометрии часто требует layout; изменение цвета — paint. Перемещение уже подготовленного слоя иногда обходится только compositing.

Разберём на примере

Если анимировать width боковой панели, соседний текст может перепереноситься на каждом кадре: меняется геометрия. При анимации transform панель может перемещаться как готовое изображение без такого пересчёта. Но создание отдельного слоя зависит от браузера и тоже расходует память.

Термины и элементы темы
DOM и CSSOM
DOM описывает документ, CSSOM — правила стилей. JavaScript может изменить оба; CSSOM не создаётся выполнением JavaScript.
Style и render tree
Вычислить применимые стили. display:none исключает элемент из layout, visibility:hidden сохраняет занимаемое место.
Layout / reflow
Вычислить размеры и положение. Изменение ширины или чтение геометрии после записи стилей может потребовать нового layout.
Paint
Подготовить отрисовку текста, фона, границ и других визуальных частей.
Compositing
Собрать подготовленные слои. Некоторые transform/opacity-анимации обходятся без нового layout и paint; это зависит от слоёв и реализации.

Коротко по теме

Layout отвечает за «где и какого размера», paint — за «что нарисовать», compositing — за сборку подготовленных слоёв. Стоимость изменения зависит от того, какие стадии придётся повторить.

Уточнение к Notion: отдельный compositor layer не гарантирован для любого transform или position:fixed; большое число слоёв расходует память.

CDN и путь через инфраструктуру

Если пользователь находится далеко от сервера, даже маленький файл может начинать загружаться с заметной задержкой. CDN — сеть промежуточных серверов, которые могут отдавать ресурсы ближе к пользователю. Важна не только скорость: CDN также уменьшает количество одинаковых обращений к исходному серверу, который называют origin.

Как это работает — по шагам

  1. Пользователь запрашивает ресурс, например logo.svg. Запрос приходит на узел CDN, а не обязательно прямо в приложение.
  2. Если на узле есть подходящая свежая копия, её можно вернуть сразу. Это cache hit. Если копии нет, cache miss ведёт к получению ресурса из origin или другого уровня кэша.
  3. Для сохранения и повторного использования нужны правила: что является ключом кэша, сколько живёт ответ и как обновить его после изменения.
  4. Ответ с личными данными нельзя бездумно использовать для всех. Авторизация, заголовки Cache-Control и различия запросов должны учитываться в политике кэша.

Разберём на примере

Файл app.abc123.js одинаков для всех посетителей и имеет имя с версией содержимого: его удобно кэшировать надолго. Ответ /api/me содержит имя текущего пользователя. Если сохранить его как общую копию только по URL, следующий пользователь может получить чужое имя.

Термины и элементы темы
CDN
Уменьшает сетевую задержку и нагрузку на origin, но требует корректных cache keys и правил инвалидирования.
Прокси и балансировщик
Прокси пересылает запросы, балансировщик распределяет их между экземплярами сервиса; функции могут совмещаться.
Кэш приватных данных
Общие кэши не должны выдавать ответ одного пользователя другому. Учитывать Cache-Control, Vary и авторизацию.

Коротко по теме

Для статики с версионированными именами поставлю CDN ближе к пользователям и разрешу длительное кэширование. Сначала измерю задержку и cache hit rate. Персональные API-ответы нельзя класть в общий кэш без правильных правил разделения и доступа.
