Оптимизация React по измерениям

Слово «тормозит» может означать медленную сеть, дорогой JavaScript, большое число DOM-узлов или layout. React memo помогает только части таких проблем. Поэтому оптимизация начинается с воспроизведения конкретного взаимодействия и измерения, где уходит время.

Как это работает — по шагам

  1. Выбери наблюдаемый сценарий: ввод символа, открытие меню, переход на страницу. Сравнивай одинаковые данные и условия до и после изменения.
  2. React Profiler показывает стоимость render/commits компонентов. Browser Performance дополняет картину задачами JavaScript, стилями, layout и paint.
  3. Ищи причину работы: общий state слишком высоко, context меняется целиком, список слишком велик, эффект создаёт дополнительные updates.
  4. После структурных исправлений можно применить memo, useMemo или useCallback, если это устраняет измеренную повторную работу. Проверить нужно не только скорость, но и правильность обновления.

Разберём на примере

Печать в поиск задерживается из-за render 5000 строк. Можно сначала локализовать state и виртуализировать список. Если дорого само вычисление фильтра, полезна другая оптимизация вычисления. useCallback у кнопки не решит ни слишком большой DOM, ни дорогой алгоритм.

Термины и элементы темы
Диагностика
React DevTools Profiler показывает commits и стоимость компонентов; browser Performance — long tasks, layout, paint и взаимодействия.
Меньше работы
Локализовать state, разделить context, убрать лишние effects, виртуализировать большие списки.
Memoization
memo пропускает некоторые parent-driven render при стабильных props; useMemo/useCallback помогают сохранять результаты/ссылки. Собственные state/context updates всё равно работают.
Приоритеты
Transitions/deferred values помогают отложить несрочный UI, но не уменьшают вычислительную сложность сами по себе.
Ad hoc проверка
Свободное исследование поведения без фиксированного тест-кейса полезно для поиска неожиданностей, но не заменяет воспроизводимый benchmark или regression test.

Коротко для собеседования

Измерение → причина → целевое изменение → повторное измерение. Меньше render не всегда означает быстрее; важно количество и стоимость фактической работы.

Core Web Vitals

Core Web Vitals описывают три заметные пользователю стороны качества страницы: когда появился главный контент, насколько быстро интерфейс реагирует и прыгают ли элементы. Это помогает связывать технические изменения с опытом человека, а не только с размером bundle или внутренними таймерами приложения.

Как это работает — по шагам

  1. LCP относится к появлению крупного видимого контента. Задержать его могут серверный ответ, позднее обнаружение изображения, его загрузка и блокирующая работа.
  2. INP оценивает задержку взаимодействия до следующего отображения. Дорогой обработчик и работа render/layout после него могут ухудшить результат.
  3. CLS оценивает неожиданные сдвиги layout. Без размеров изображения браузер может сначала разместить текст, а затем сдвинуть его, когда узнает размер картинки.
  4. Полевые данные собираются у реальных посетителей с разными устройствами и сетями. Лабораторный тест полезен для диагностики, но не заменяет такое распределение пользователей.

Разберём на примере

Если карточки прыгают при загрузке фото, первым делом проверь зарезервированные размеры — это связано с CLS. Если фото не прыгает, но долго отсутствует, смотри LCP и цепочку загрузки. Если клик по фильтру долго не отражается на экране, исследуй INP и работу основного потока.

Термины и элементы темы
LCP
Largest Contentful Paint: хороший ориентир ≤ 2.5 секунды. Проверить TTFB, discovery и загрузку главного изображения/текста.
INP
Interaction to Next Paint: ≤ 200 мс. Проверить длинные задачи, обработчики и стоимость следующего render.
CLS
Cumulative Layout Shift: ≤ 0.1. Резервировать место под изображения, рекламу и динамические блоки.
Оценка
Порог оценивают на 75-м перцентиле, отдельно по mobile/desktop; не выдавать единичный Lighthouse-прогон за полевой результат.

Коротко для собеседования

LCP — появление главного контента, INP — отзывчивость, CLS — стабильность. Для каждой метрики нужна своя причина и проверка, а не одна универсальная оптимизация.

Bundle и загрузка ресурсов

Bundle объединяет код и зависимости в форму для доставки браузеру. Но пользователь платит не только за скачивание: код нужно разобрать и выполнить. Иногда меньший bundle помогает, а иногда проблема в тяжёлой работе уже загруженного кода. Эти стоимости нужно различать.

Как это работает — по шагам

  1. Посмотри, что попало в стартовую загрузку: код текущего экрана, редко используемые editors, крупные библиотеки и повторяющиеся зависимости.
  2. Code splitting отделяет части, которые не нужны сразу. Dynamic import загружает соответствующий chunk, когда приложение действительно доходит до этой возможности.
  3. Tree shaking удаляет неиспользуемую часть совместимого module graph; compression уменьшает передаваемые bytes. Это разные процессы и не заменяют друг друга.
  4. Слишком поздняя загрузка критичного ресурса тоже вредна. Лениво загружать editor по нажатию удобно; откладывать главное изображение страницы — возможное ухудшение LCP.

Разберём на примере

Большой редактор нужен только при нажатии «Редактировать». Его можно вынести в отдельный chunk и показать fallback загрузки. Если же библиотека нужна сразу для первого экрана, дробление может добавить цепочку ожиданий. Решение проверяется по waterfall, bytes и времени исполнения.

Термины и элементы темы
Code splitting
Разделить по маршрутам или тяжёлым функциям через import(); не дробить вслепую на множество маленьких запросов.
Tree shaking
Удаление неиспользуемых exports при подходящей структуре modules и sideEffects; minification — отдельное преобразование.
Compression и caching
Brotli/gzip уменьшают передачу; content-hash filenames помогают долгому кэшированию.
Preload / prefetch / lazy
Preload для критичного текущего ресурса, prefetch для вероятного будущего; lazy для некритичного. Не делать LCP-изображение ленивым.

Коротко для собеседования

Оптимизация bundle сочетает состав кода, момент загрузки, кэширование и стоимость выполнения. «Разбить всё» и «включить gzip» — не полный план.

Compiler, transpiler и bundler

В цепочке сборки несколько разных работ: понять синтаксис, преобразовать код, проверить типы, связать импорты и подготовить файлы для доставки. Один инструмент может совмещать функции, поэтому названия compiler и bundler не всегда соответствуют разным исполняемым программам.

Как это работает — по шагам

  1. Преобразование TS/JSX делает исходник исполнимым для целевой среды. Быстрое удаление аннотаций типов не обязательно включает проверку их корректности.
  2. Typecheck анализирует совместимость типов и должен быть отдельно предусмотрен, если выбранный трансформер этим не занимается.
  3. Bundler строит граф зависимостей, решает импорты, формирует chunks и подключает обработку assets. Plugins расширяют эту цепочку.
  4. Инструменты monorepo управляют задачами и проектными зависимостями. Кэш успешной сборки не является ни компиляцией языка, ни runtime-кэшем приложения.

Разберём на примере

Проект может быстро показать TSX в браузере после transformation, но всё ещё содержать type error. Поэтому успешный dev preview не доказывает, что tsc --noEmit пройдёт. Аналогично смена bundler не исправит дорогой React render: это другая стадия жизни приложения.

Термины и элементы темы
Compiler / transpiler
Преобразовать исходный код: TS/JSX, синтаксис, оптимизации. Удаление TS-аннотаций не обязательно означает typecheck.
Bundler
Построить dependency graph, собрать chunks, обработать assets, code splitting и plugins.
Семейства
Webpack/Rspack, Rollup/Rolldown, esbuild и Turbopack — инструменты со своими возможностями и совместимостью; выбирать по проекту, не только по языку реализации.
Monorepo tools
Nx управляет графом проектов, задачами и кэшем; не является прямой заменой bundler. .mjs — явный ESM в Node, .js зависит от окружения/package type, .ts требует TS-tooling.

Коротко для собеседования

Различай преобразование кода, typecheck, упаковку и оркестрацию задач. Для оценки инструмента важно, какую именно работу он выполняет в вашем pipeline.

Ошибки, traces, metrics и dashboards

После релиза ошибка существует на чужом устройстве, и её нельзя всегда воспроизвести локально. Observability помогает восстановить происходившее по сигналам приложения: ошибкам, метрикам, логам и traces. Разные сигналы дают разную детализацию, поэтому полезно понимать роль каждого инструмента.

Как это работает — по шагам

  1. Метрика — число во времени: например, доля ошибок или длительность запроса. Она помогает заметить изменение состояния системы, но не всегда объясняет один конкретный случай.
  2. Trace связывает отдельные операции — spans — в путь запроса. Context propagation позволяет соотнести действия разных компонентов системы.
  3. Ошибка со stack trace, release и breadcrumbs показывает место и предшествующие действия. Source maps помогают связать собранный production-код с исходным.
  4. Инструментация создаёт данные, backend их принимает/хранит, dashboard визуализирует. Секреты и лишние персональные данные не должны попадать в telemetry.

Разберём на примере

После релиза выросло время открытия заказа. Метрики показывают момент ухудшения, trace помогает увидеть медленный участок, а Sentry может связать сбой с конкретным stack и release. OpenTelemetry стандартизирует сбор/передачу сигналов; Grafana помогает просматривать подключённые данные.

Термины и элементы темы
OpenTelemetry
Инструментация и передача traces/metrics/logs; span описывает операцию, trace связывает их через context propagation.
Sentry
Ошибки, stack traces, breadcrumbs, releases и инструменты performance; source maps помогают связать production stack с исходниками.
Prometheus
Сбор и хранение временных рядов метрик; важно контролировать cardinality labels.
Grafana
Визуализация и alerting по подключённым источникам данных; не заменяет instrumentation.

Коротко для собеседования

Сначала вопрос: «что сломалось», «как часто», «где потрачено время». Затем подходящий сигнал и инструмент. Dashboard не заменяет корректный сбор данных.
