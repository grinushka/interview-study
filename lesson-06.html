Promise и async/await

Promise — объект, через который код узнаёт будущий результат операции. Его можно получить сейчас, когда результат ещё не готов, и заранее описать, что делать при успехе или ошибке. Сам Promise не является отдельным потоком и не означает, что вся работа внутри него выполняется позже.

Как это работает — по шагам

  1. Создание new Promise сразу вызывает executor. Он получает resolve и reject, с помощью которых передаёт результат. Начальное состояние — pending; после завершения — fulfilled или rejected.
  2. then не возвращает результат исходной операции напрямую: он создаёт следующий Promise. Возвращаемое значение callback становится результатом следующего звена; выброшенная ошибка делает это звено rejected.
  3. async-функция тоже возвращает Promise. Она выполняется до точки приостановки await, а продолжение запускается позже. Остальной код не обязан ждать её, пока сам не использует await или then.
  4. Ошибки нужно связывать с цепочкой и обрабатывать. Просто запустить async-функцию без обработки результата — не то же самое, что защитить её окружающим синхронным try/catch.

Разберём на примере

Функция loadUser возвращает Promise. Код экрана может сразу показать загрузку, а затем по успеху сохранить пользователя и по ошибке показать сообщение. await делает запись последовательной внутри async-функции, но не останавливает браузер на всё время сетевого ожидания.

console.log("start");
const p = new Promise(resolve => {
  console.log("executor");
  resolve(7);
});
p.then(value => console.log(value));
console.log("end");
// start → executor → end → 7
  1. Executor вызывается во время new Promise, поэтому executor появляется до end.
  2. resolve(7) задаёт результат, но не выполняет зарегистрированный then прямо в текущей строке.
  3. Реакция then выполняется после текущего синхронного кода.
Термины и элементы темы
then / catch / finally
then создаёт новый Promise; возвращённое значение продолжает цепочку, throw отклоняет её. catch обрабатывает rejection; finally обычно пропускает прежний результат, но может заменить его ошибкой.
async / await
async всегда возвращает Promise. await приостанавливает конкретную async-функцию, а не весь поток; продолжение выполняется асинхронно.
Запуск и отмена
Promise сам по себе не означает отдельный поток. Комбинаторы не отменяют другие операции; fetch отменяют через AbortController.
Дополнительные static методы
resolve и reject создают результат; withResolvers даёт promise/resolve/reject; try оборачивает синхронный или асинхронный результат вызова. Доступность проверять для целевых браузеров.

Коротко для собеседования

Promise описывает будущий результат и цепочку обработки. Executor синхронен; реакции и продолжение await асинхронны. async/await — удобная форма работы с Promise, а не другой механизм параллельности.

Четыре комбинатора Promise

Комбинатор объединяет результаты нескольких Promise в один итоговый Promise. Выбор зависит от того, что считается достаточным результатом: все успехи, полный отчёт, первый успех или первое завершение любого вида. Большинство различий легко увидеть на одной и той же временной шкале.

Как это работает — по шагам

  1. Пусть A успешно завершится через 100 мс, B отклонится через 20 мс, C успешно завершится через 50 мс. Это три независимо запущенные операции.
  2. all отклонится на ошибке B. allSettled дождётся всех трёх и вернёт отчёт для A, B и C в порядке входа, а не завершения.
  3. race завершится ошибкой B: это первое завершение любого вида. any проигнорирует rejection B и вернёт успех C, не дожидаясь A.
  4. Ни один из этих исходов автоматически не останавливает остальные операции. Если all уже отклонился, A и C могут продолжать работу и иметь свои побочные эффекты.

Разберём на примере

Для страницы, которой одновременно нужны пользователь и настройки, подходит all. Для отчёта о загрузке десяти независимых файлов — allSettled. Для первого успешного ответа зеркал — any. Для соревнования запроса с таймером — race, но отмену проигравшего запроса нужно организовать отдельно.

Термины и элементы темы
Promise.all
Ждёт все fulfillment и возвращает массив значений; отклоняется при первом rejection. Пустой набор даёт fulfilled [] без ожидания, обработчик then всё равно асинхронный.
Promise.allSettled
Ждёт settlement всех и возвращает записи status + value/reason. Rejection отдельной входной операции сам по себе не отклоняет итог.
Promise.any
Возвращает первый fulfillment; если все rejected — AggregateError. Пустой iterable также даёт rejection с AggregateError.
Promise.race
Повторяет первый settlement: fulfillment или rejection. Пустой iterable оставляет результат pending.

Коротко для собеседования

all — все успехи; allSettled — отчёт обо всех; any — первый успех; race — первое завершение. Дополнительно нужно помнить порядок результатов, пустой вход и отсутствие автоматической отмены.

Event loop: task и microtask

Внутри одного JavaScript agent текущий синхронный код выполняется до освобождения стека. Таймер не может вклинить callback посередине выполняющейся функции. Когда текущая работа закончена, среда выбирает дальнейшие действия; microtasks имеют особый порядок обработки относительно следующей task.

Как это работает — по шагам

  1. Сначала выпиши весь синхронный вывод. Вызов setTimeout только планирует будущую задачу; регистрация then тоже не выполняет его callback немедленно.
  2. Когда стек освободился и наступил microtask checkpoint, выполняются готовые реакции Promise и queueMicrotask.
  3. Если microtask добавила ещё одну microtask, очередь продолжает обрабатываться. Она должна опустеть до перехода к следующей обычной задаче.
  4. Готовый callback таймера выполнится в следующей подходящей task. Возможности отрисовки зависят от браузерного цикла; длинная синхронная работа и бесконечные microtasks могут задержать экран.

Разберём на примере

В коде ниже A и E печатаются сразу. C уже ждёт в microtasks. Во время C туда добавляется D, и D тоже выполняется до задачи таймера B. Нулевая задержка B не делает её приоритетнее microtasks.

console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => {
  console.log('C');
  queueMicrotask(() => console.log('D'));
});
console.log('E');
Термины и элементы темы
Task
Например callback таймера или обработка события. Таймер задаёт минимальную задержку до готовности, а не точное время исполнения.
Microtask
then/catch/finally и продолжение await, а также queueMicrotask. Новые microtasks в очереди выполняются в том же checkpoint.
Rendering
Не является отдельной microtask; браузер выбирает rendering opportunities. Длинная очередь microtasks может задержать UI.

Коротко для собеседования

При разборе вывода отдельно отслеживай стек, microtasks и tasks. Для этого примера порядок A → E → C → D → B объясняется очередями, а не скоростью выполнения Promise.

setTimeout, setInterval и stale closure

Таймер сообщает среде, что callback можно выполнить не раньше определённого времени. Он не резервирует точный момент на процессоре. Если поток занят, callback подождёт. Это объясняет и неточность времени, и проблемы с повторяющимися асинхронными операциями.

Как это работает — по шагам

  1. setTimeout планирует один callback. setInterval создаёт повторяющееся расписание. Их ID нужен, чтобы отменить ещё ненужную работу.
  2. Если внутри interval запускается fetch, сам callback может быстро закончиться, а fetch продолжит ждать. Следующий interval запустит ещё один запрос до завершения предыдущего.
  3. Для строго последовательной проверки можно после завершения текущей операции поставить следующий timeout. Тогда новая операция не начинается по старому расписанию параллельно ожидающей.
  4. В React таймер также связан с замыканием. Callback render, где count был равен 0, продолжает видеть это значение, если не организовано получение актуального state.

Разберём на примере

Счётчик с setCount(count + 1) внутри однажды созданного interval может постоянно вычислять 0 + 1. setCount(c => c + 1) передаёт React функцию от актуального предыдущего состояния. При unmount нужно остановить interval, иначе работа продолжится после ухода со страницы.

useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1);
  }, 1000);
  return () => clearInterval(id);
}, []);
  1. В callback не читается count из старого render; React получает updater от предыдущего state.
  2. ID хранится в окружении эффекта, чтобы cleanup остановил именно этот interval.
  3. Пример относится к независимому счётчику; для чтения других props/state зависимости всё равно нужно анализировать.
Термины и элементы темы
setTimeout
Однократный callback после минимальной задержки. В background и вложенных таймерах браузер может увеличивать задержку.
setInterval
Повторяющиеся callbacks, но не гарантия точного интервала. Для последовательных async-запросов безопаснее планировать следующий timeout после завершения.
React и замыкание
Callback захватывает значения конкретного render. Для обновления от предыдущего state помогает functional updater; подписки требуют cleanup.

Коротко для собеседования

Таймер задаёт минимальное ожидание, а не точный запуск. Для async-повторов думай о перекрытии запросов; для React — о замыкании и cleanup.

Fetch и Streams

Обычный response.json() удобен, когда ответ разумного размера и нужен целиком. Поток нужен, когда результат хочется обрабатывать постепенно: например, отображать приходящий текст или читать большой файл. Взамен приложение берёт на себя работу с границами частей и промежуточными ошибками.

Как это работает — по шагам

  1. fetch сначала даёт Response с заголовками и доступом к body. Сам HTTP-статус 404 не делает этот Promise rejected: status или ok проверяет приложение.
  2. У body можно получить reader. Каждый read() возвращает очередную порцию bytes или done. Это транспортная порция, не обязательно одна строка или один JSON-объект.
  3. Текст может содержать многобайтные символы. Если символ разделён на два chunks, нужен decoder, сохраняющий незавершённые bytes между чтениями.
  4. Формат сообщений разбирается отдельно: приложение может копить buffer до разделителя строки. Нужно предусмотреть отмену, освобождение reader и ошибку в середине уже начатого вывода.

Разберём на примере

Сервер прислал строки JSON, разделённые переводом строки. Первый chunk закончился посередине объекта. Нельзя выполнить JSON.parse на каждом chunk: нужно накопить данные до целой строки, разобрать завершённую строку и оставить остаток для следующего чтения.

Термины и элементы темы
Проверка ответа
Проверить response.ok/status и доступность body. json()/text() обычно потребляют тело целиком.
Чтение
ReadableStream.getReader() и read() дают chunks до done. TextDecoder с stream:true или TextDecoderStream сохраняет границы многобайтных символов.
Управление
Учитывать backpressure, ошибки и отмену через AbortController. Граница chunk не равна границе JSON-сообщения; нужен framing/буфер.

Коротко для собеседования

Streams позволяют работать частями, но не дают готовый формат сообщений. Разделяй получение bytes, декодирование текста и разбор структуры данных.
