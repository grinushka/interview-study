HTTP и API

HTTP-запрос и ответ

HTTP можно представить как договор о форме запроса и ответа. Клиент должен сообщить, что хочет сделать и с каким ресурсом. Сервер должен сообщить результат и, когда нужно, вернуть данные. Заголовки дополняют основной смысл: например, объясняют, что тело содержит JSON или как разрешено его кэшировать.

Как это работает — по шагам

  1. В запросе метод задаёт семантику действия, адрес выбирает ресурс, заголовки передают параметры протокола, а body содержит основную полезную нагрузку, если она нужна.
  2. В ответе статус описывает результат на уровне HTTP. Заголовки сообщают метаданные, а body может содержать страницу, изображение, JSON или описание ошибки.
  3. Query находится в URL. Он удобен, когда состояние должно быть частью ссылки: поиск, сортировка, номер страницы. Body удобен для структурированных данных создания или изменения.
  4. HTTPS защищает и query, и body в пути, но это не делает их невидимыми во всех остальных местах. URL может остаться в истории, аналитике или серверных логах.

Разберём на примере

GET /products?category=books&page=2 просит выборку товаров и позволяет скопировать ссылку. POST /orders с JSON в body передаёт состав нового заказа. Это соглашение API: само наличие body не делает запрос безопасным или корректным.

Термины и элементы темы
Запрос
Метод, адрес ресурса, заголовки и необязательное тело. В HTTP/2 и HTTP/3 представление бинарное, а не текстовая start line.
Ответ
Статус, заголовки и необязательное тело. Заголовки описывают формат, кэш, cookies и политики.
Query и body
Query — часть URL, удобная для фильтрации и ссылок; body — содержимое запроса, например JSON. HTTPS шифрует оба при передаче, но URL может попасть в историю и логи.

Коротко по теме

Запрос — метод, адрес, заголовки и необязательное тело. Ответ — статус, заголовки и необязательное тело. Query и body отличаются местом и назначением, а не наличием шифрования.

MDN: HTTP

Методы HTTP и идемпотентность

HTTP-методы нужны, чтобы действие можно было понять не только из произвольного имени URL. GET должен читать представление, PUT — задавать состояние ресурса, DELETE — удалять. Этим смыслом пользуются клиенты, кэши и инфраструктура. Важное следствие — возможность безопасно рассуждать о повторной отправке запроса после сетевого сбоя.

Как это работает — по шагам

  1. Сначала различай safe и idempotent. Safe означает, что клиент не запрашивает изменение состояния. Идемпотентность означает, что повтор того же действия имеет тот же предполагаемый эффект, что и один вызов.
  2. Повтор PUT с тем же полным состоянием оставляет ресурс в том же состоянии. Повтор DELETE не делает ресурс «ещё более удалённым». Ответ при этом может измениться.
  3. POST не даёт общей гарантии идемпотентности. Повтор отправки заказа может создать два заказа, если API специально не обрабатывает повторы.
  4. PATCH описывает частичное изменение. Операция «установить likes=5» и операция «увеличить likes на 1» имеют разное поведение при повторе.

Разберём на примере

Клиент отправил DELETE /cart/items/7. Сервер удалил товар, но ответ потерялся. Повторный DELETE может вернуть 404: товар уже отсутствует. Эффект одинаков — товара нет. Если потерялся ответ на POST /orders, повтор без защиты способен создать второй заказ; здесь полезен idempotency key.

Термины и элементы темы
GET
Получить представление. Safe и идемпотентный; сервер не должен использовать его для изменения бизнес-состояния.
HEAD
Семантика GET без тела ответа. Проверка метаданных; отдельные заголовки, вычисляемые при генерации тела, могут отсутствовать.
POST
Передать данные для обработки. По общему контракту не идемпотентный; API может добавить idempotency key.
PUT
Создать или заменить состояние ресурса по известному URI. Идемпотентный.
PATCH
Применить частичные изменения. Идемпотентность зависит от операции: присвоить значение и увеличить счётчик — разные случаи.
DELETE
Удалить связь ресурса с URI. Идемпотентный по эффекту, даже если второй ответ — 404.
OPTIONS
Узнать доступные варианты взаимодействия; используется в CORS preflight.

Коротко по теме

Идемпотентность — свойство эффекта операции, а не одинаковости HTTP-статуса или текста ответа. Это помогает решать, когда допустим повтор запроса.

Уточнение к Notion: повторный ответ не обязан совпадать с первым; POST не обязательно создаёт ресурс, а ETag не обязан быть хэшем.

MDN: HTTP methods

Классы статусов HTTP

Статус HTTP помогает клиенту понять, как продолжить работу. Одного сообщения «что-то пошло не так» обычно недостаточно: пользователь мог потерять доступ, указать несуществующий адрес или столкнуться с временным сбоем сервиса. Классы статусов группируют такие результаты, а конкретный код уточняет ситуацию.

Как это работает — по шагам

  1. Первый разряд задаёт класс: 1xx — промежуточная информация, 2xx — успех, 3xx — перенаправление и связанные с представлениями ответы, 4xx — проблема запроса/доступа, 5xx — проблема обработки сервером.
  2. 401 означает, что запросу не хватает подходящих credentials: например, сессия истекла. 403 означает отказ в доступе; повторный login не обязательно поможет.
  3. 404 говорит, что целевой ресурс не найден или сервер не раскрывает его существование. Это отличается от временной недоступности всего сервиса.
  4. Для UI важен ещё контракт API: один и тот же статус может сопровождаться машинным кодом ошибки и подробностями. Не стоит определять логику по произвольному тексту сообщения.

Разберём на примере

При 401 приложение может предложить войти снова. При 403 — объяснить отсутствие прав. При 429 — учесть ограничение частоты и Retry-After, если он есть. При 503 — показать временную недоступность и контролируемое повторение, а не бесконечно отправлять запросы.

Термины и элементы темы
1xx
Информация о промежуточной обработке: 100 Continue; 101 Switching Protocols используется при классическом WebSocket upgrade.
2xx
Успех: 200 OK, 201 Created, 204 No Content.
3xx
Перенаправление и работа с представлениями: 301/308 постоянный redirect, 302/307 временный, 304 Not Modified — повторно использовать кэш.
4xx
Ошибка запроса/доступа: 400, 401 — отсутствуют подходящие credentials, 403 — доступ запрещён, 404, 409 — конфликт, 429 — ограничение частоты.
5xx
Проблема сервера: 500, 502 — некорректный ответ upstream, 503 — временно недоступен, 504 — timeout upstream.

Коротко по теме

1xx — промежуточная информация, 2xx — успех, 3xx — перенаправление или работа с сохранённым представлением, 4xx — проблема запроса со стороны клиента, 5xx — ошибка сервера. 401 требует корректной аутентификации; 403 означает отказ в доступе; 404 — ресурс не найден; 500 — внутренняя ошибка; 503 — временная недоступность. Интерфейс выбирает действие по конкретному коду и контракту API.

HEAD, заголовки и 304

Кэш хранит ответ, чтобы не загружать одинаковые данные заново. Но «ответ есть» и «его можно использовать сейчас» — разные вопросы. Браузеру нужно понять, достаточно ли свежая копия и не изменилась ли она на сервере. Поэтому правила свежести и проверка версии — два разных механизма.

Как это работает — по шагам

  1. При первом ответе сервер может передать Cache-Control и валидатор версии: ETag или Last-Modified. Браузер сохраняет данные вместе с метаданными.
  2. Если политика позволяет считать копию свежей, браузер использует её без повторной передачи тела по сети.
  3. Если копия требует проверки, браузер отправляет условный запрос. If-None-Match содержит прежний ETag; сервер сравнивает его с текущей версией.
  4. При совпадении сервер возвращает 304 без нового тела. Браузер использует сохранённое тело с обновлёнными метаданными. При изменении получает новый ответ, обычно 200.

Разберём на примере

Ты скачала аватар размером 200 KB с ETag "v1". Позже отправляешь GET с If-None-Match: "v1". Сервер отвечает 304: снова передавать 200 KB не нужно. HEAD тоже позволяет получить метаданные без тела, но добавлять отдельный HEAD перед каждым GET обычно означает лишний запрос.

Термины и элементы темы
Описание представления
Content-Type — формат; Content-Length — размер тела в байтах, если известен; Content-Encoding — кодирование; Content-Language — язык.
Cache-Control
max-age задаёт свежесть; no-cache требует проверки перед повторным использованием; no-store запрещает хранение. private ограничивает общие кэши.
ETag / If-None-Match
Сервер задаёт непрозрачный валидатор версии; клиент возвращает его для проверки. Валидатор не обязан быть хэшем.
Last-Modified / If-Modified-Since
Дата изменения и условная проверка по времени. Имеет ограниченную точность.
Другие заголовки HEAD
Location — redirect; Accept-Ranges — диапазоны; Date/Server — метаданные; Set-Cookie — cookie; CSP/HSTS — политики; Access-Control-* — CORS.

Коротко по теме

Cache-Control определяет правила повторного использования. Валидатор помогает проверить версию. no-cache разрешает хранение с проверкой; no-store запрещает хранение ответа.

Уточнение к Notion: no-cache не означает «не хранить»; no-store — отдельная директива. HEAD не заменяет условный GET автоматически.

REST и RESTful API

REST описывает архитектурные ограничения взаимодействия распределённых компонентов. Для собеседования важно понимать их смысл, а не только перечислить HTTP-методы. Ресурс — понятие предметной области, например заказ. Представление — данные о нём, например JSON; это не обязательно прямое отражение внутреннего устройства сервера.

Как это работает — по шагам

  1. Клиент и сервер разделяют ответственность и общаются через понятный интерфейс. Клиенту не нужно знать, как внутри хранится заказ.
  2. Каждый запрос несёт контекст, необходимый для его обработки. Сервер не должен полагаться на скрытый диалог вида «предыдущим запросом этот клиент выбрал заказ №7».
  3. Единообразный интерфейс позволяет распознавать ресурсы, передавать их представления и понимать сообщения. В строгом REST доступные дальнейшие действия также обнаруживаются через гипермедиа.
  4. Кэшируемость и многослойность позволяют повторно использовать ответы и добавлять посредников без обязательного знания о них у клиента. Передача кода клиенту — необязательное ограничение.

Разберём на примере

GET /orders/7 получает представление заказа. Запрос на изменение содержит и нужную идентификацию, и данные операции. Если несколько запросов обрабатывают разные экземпляры сервера, им не требуется восстанавливать неявную последовательность команд клиента. При этом сервер, конечно, продолжает хранить сами заказы.

Термины и элементы темы
Client–server
Разделить интерфейс клиента и ответственность сервера.
Stateless
Запрос содержит контекст, нужный для его обработки; это не запрещает серверу хранить ресурсы и бизнес-данные.
Cacheable
Ответ сообщает возможность повторного использования.
Uniform interface
Идентификация ресурсов, работа с представлениями, самодостаточные сообщения и гипермедиа как двигатель состояния приложения.
Layered system
Клиенту не требуется знать обо всех промежуточных слоях.
Code on demand — необязательно
Сервер может расширить возможности клиента передаваемым кодом; это единственное необязательное ограничение REST.

Коротко по теме

REST — набор ограничений архитектуры, а не синоним JSON API. Stateless относится к контексту взаимодействия, а не к запрету хранить бизнес-данные.

Дополнение к Notion: включены необязательный code-on-demand и гипермедиа в uniform interface, часто опускаемые в кратких конспектах.

REST, SOAP, GraphQL и gRPC

Разные API-подходы по-разному отвечают на вопрос «как клиент выражает, что ему нужно». В REST он обычно работает с ресурсами. В RPC вызывает именованную операцию удалённого сервиса. В GraphQL выбирает поля через типизированную схему. Сравнивать их полезно по контракту и потребностям клиента, а не по принципу «новее — лучше».

Как это работает — по шагам

  1. У REST заранее определены ресурсы и представления. Если клиенту нужны данные из нескольких ресурсов, может потребоваться несколько запросов или специально подготовленный endpoint.
  2. GraphQL даёт клиенту выбирать поля в рамках схемы. Это уменьшает некоторые случаи лишних данных, но сервер всё равно должен эффективно получить их и ограничивать дорогие запросы.
  3. gRPC описывает сервис и методы, генерирует клиентский/серверный код и поддерживает разные виды streaming. Для браузера нужно учитывать ограничения native gRPC и gateway.
  4. SOAP задаёт XML-формат сообщений и связанные стандарты. Он может быть необходим в существующей интеграции, даже если для нового browser API выбрали бы другой подход.

Разберём на примере

Экран показывает имя автора и заголовки его статей. REST может потребовать /users/7 и /users/7/posts либо отдельное представление экрана. GraphQL позволяет запросить нужные поля за один запрос. Это не гарантирует один внутренний запрос сервера: плохо организованные resolvers могут создать множество обращений.

Термины и элементы темы
REST
Ресурсы и представления, стандартная семантика HTTP, естественное HTTP-кэширование.
SOAP
Протокол сообщений на основе XML с формальным контрактом и расширениями; может работать не только поверх HTTP.
GraphQL
Схема с типами; query читает выбранные поля, mutation изменяет данные, subscription доставляет обновления. Нужны контроль сложности запросов и решение N+1.
gRPC
RPC с описанием сервисов, часто Protocol Buffers, генерацией кода и streaming. Обычный браузер не вызывает native gRPC напрямую: нужен gRPC-Web или другой gateway.

Коротко по теме

REST описывает архитектурные ограничения работы с ресурсами; SOAP задаёт XML-сообщения и протокол; GraphQL позволяет клиенту выбрать поля по схеме; gRPC задаёт RPC-контракт, часто через Protobuf. Для браузера у gRPC нужен подходящий gateway/gRPC-Web. Выбор зависит от клиентов, контракта и транспорта, а не от формата JSON против XML.

Offset и cursor pagination

Список может содержать тысячи элементов, поэтому API отдаёт его порциями. Нужно договориться не только о размере порции, но и о том, как найти следующую. Проблема особенно заметна, если между запросами добавляются или удаляются записи: числовая позиция элемента может измениться.

Как это работает — по шагам

  1. Offset говорит «пропусти N записей». Для страницы 3 по 20 элементов это часто offset=40. Такой интерфейс удобен для перехода по номерам страниц.
  2. Если перед уже прочитанной частью добавили новую запись, позиции смещаются. Следующий offset может повторно захватить старый элемент или пропустить другой.
  3. Cursor описывает границу продолжения. При сортировке по времени и ID он может обозначать «следующие элементы после этой пары значений».
  4. Порядок должен быть однозначным. Одной даты недостаточно, если несколько записей имеют одинаковую дату; добавляют уникальный tie-breaker, например ID.

Разберём на примере

В ленте сначала видны записи 100…81. Пока читаешь, появились новые 102 и 101. Offset=20 уже указывает не туда, куда до вставки. Cursor «после записи 81» лучше выражает желание продолжить старую ленту. Но если меняется само поле сортировки, нужны дополнительные правила согласованности.

Термины и элементы темы
Offset
Пропустить N элементов и взять следующую порцию. Удобны номера страниц, но вставки и удаления смещают границы.
Cursor
Продолжить после позиции из cursor, например пары createdAt/id. Лучше подходит для ленты, но произвольный переход на страницу сложнее.
Ограничения
Cursor не гарантирует snapshot и отсутствие любых повторов при изменении сортировочных полей. Клиенту иногда всё равно нужна дедупликация по ID.

Коротко по теме

Для меняющейся бесконечной ленты выберу cursor по стабильному порядку, например createdAt + id. Следующая порция начинается после последнего элемента. Offset проще для страниц с номерами, но вставка перед текущей позицией может дать повторы. Cursor не гарантирует snapshot: это отдельное требование к API.

HTTP/1.1, HTTP/2 и HTTP/3

Версии HTTP сохраняют знакомую семантику: методы, статусы, заголовки и тела. В основном меняется способ передачи сообщений. Когда страница требует десятки ресурсов, способ совместного использования соединения влияет на задержки и на то, как потеря данных в сети затрагивает соседние запросы.

Как это работает — по шагам

  1. HTTP/1.1 умеет постоянные соединения. Но последовательность ответов и ограничения pipelining мешают свободно перемешивать независимые ответы в одном соединении.
  2. HTTP/2 разбивает обмен на бинарные frames и логические потоки. Несколько ответов могут передаваться вперемешку по одному соединению: это multiplexing.
  3. При HTTP/2 под потоками находится общий TCP. Потеря части TCP-данных может задержать доставку данных других HTTP-потоков, даже если их frames уже пришли.
  4. HTTP/3 использует QUIC поверх UDP. Надёжная доставка организуется по потокам QUIC, что уменьшает связанную с потерями блокировку независимых потоков.

Разберём на примере

Страница одновременно загружает CSS, JS и несколько изображений. HTTP/2 позволяет не ждать полного ответа на один ресурс перед передачей частей другого в том же соединении. Если сеть теряет пакет, у TCP остаётся общая упорядоченная доставка. Именно этот уровень ограничения меняет HTTP/3.

Термины и элементы темы
HTTP/1.1
Текстовые сообщения и persistent connections; браузеры часто открывают несколько TCP-соединений. Pipelining имеет ограничения и head-of-line blocking.
HTTP/2
Бинарные frames, multiplexing потоков в одном соединении, HPACK для headers. Потеря TCP-пакета может задержать все потоки соединения.
HTTP/3
QUIC поверх UDP, встроенный TLS и независимые потоки транспорта, QPACK. Не использует TCP; потери всё равно могут влиять на congestion control.

Коротко по теме

HTTP/2 даёт multiplexing поверх TCP; HTTP/3 — поверх QUIC. Говорить «HTTP/1.1 всегда создаёт новое соединение на каждый запрос» неверно.

Уточнение к Notion: HTTP/1.1 умеет persistent connections; формулировка «одно соединение на запрос» неверна.
