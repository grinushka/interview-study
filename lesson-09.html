React: состояние и данные

Context и разделение контекстов

Context позволяет передавать значение глубоко по дереву без ручного prop на каждом промежуточном уровне. Потребитель подписывается на значение ближайшего provider. Это удобно для темы или текущего пользователя, но не означает автоматическую точечную подписку на каждое поле объекта.

Как это работает — по шагам

  1. Provider задаёт value. useContext в дочернем компоненте читает его и подписывает компонент на соответствующий context.
  2. Если value изменился по Object.is, потребители уведомляются. Если value — новый объект при каждом render, даже одинаковые поля не делают ссылку прежней.
  3. Компонент, читающий только theme из большого context, всё равно подписан на значение этого context целиком. Частое изменение search в том же объекте может затронуть его.
  4. Разделяй независимые значения и частоты обновления. Memoization value помогает со случайной сменой ссылки, но не должна скрывать реальное изменение данных.

Разберём на примере

В AppContext лежат user, theme и текст поиска. Поле поиска обновляется на каждый символ; кнопка темы читает из этого же context. Разделение SearchContext и ThemeContext уменьшит связанные уведомления. Это не исключает обычные render от родителя — их нужно рассматривать отдельно.

Термины и элементы темы
Разделение
Разные контексты для независимых данных и разной частоты обновления: тема, пользователь, часто меняющийся ввод.
Ссылка value
Новый объект {user, logout} при render может уведомить потребителей; memoization value/callback полезна после измерений.
Границы
Context передаёт значение и подписку, но не даёт selectors по отдельным полям автоматически. Обычный render родителя тоже может вызывать дочерние render.

Коротко по теме

Context снимает prop drilling, но не является встроенной системой selectors по полям. Разделение контекстов помогает управлять связанностью данных и обновлений.

React: useContext

Организация состояния

Производительность часто зависит от того, где лежит state и сколько компонентов он затрагивает. Прежде чем оборачивать всё в memo, полезно убрать лишние источники обновлений и дублирование данных. Хорошая структура state также упрощает корректность: меньше значений приходится поддерживать согласованными.

Как это работает — по шагам

  1. Определи минимальные исходные данные. Если filteredItems можно вычислить из items и query, отдельный state для filteredItems часто создаёт ненужную синхронизацию.
  2. Расположи state ближе к компонентам, которым он нужен. Временный ввод одной формы не обязан жить в корне всего приложения.
  3. Если данные нужны нескольким компонентам, подними их до ближайшего общего владельца. Общий доступ сам по себе не требует глобального store.
  4. Отделяй UI-state от server state. Открытый dropdown и кэш ответа API имеют разные требования к свежести, ошибкам и повторной загрузке.

Разберём на примере

Если query находится в App, каждый символ может запускать render большой страницы. Если поле и результаты объединены отдельным SearchPanel, обновление можно ограничить этой областью. Тяжёлые независимые части страницы получают меньше причин пересчитываться.

Термины и элементы темы
Локальность
State поля ввода внутри формы не должен без причины перерисовывать всю страницу.
Единый источник
Не дублировать одинаковые данные в нескольких state. Выбранный объект часто лучше хранить как ID.
Композиция
Разделить часто меняющуюся и тяжёлую части; передача children иногда сохраняет стабильное поддерево.
Server state
Удалённые данные имеют freshness, retries, cache и invalidation; это другой жизненный цикл, чем открытый dropdown.

Коротко по теме

State строки поиска держу рядом с input и не поднимаю его выше необходимого. Список вычисляю из query и исходных items, не дублируя отфильтрованные данные в state. Если тяжёл именно render списка, измерю и рассмотрю виртуализацию, memo и deferred update; это разные меры против разных причин.

React: choosing state structure

Flux, Redux и middleware

Когда много частей приложения читают и изменяют общие данные, становится трудно понять, откуда пришло изменение. Redux делает этот путь явным: UI сообщает о событии, reducer рассчитывает следующее состояние, подписчики читают результат. Предсказуемость появляется из правил потока, а не просто из единственного большого объекта.

Как это работает — по шагам

  1. UI вызывает dispatch с action — описанием произошедшего события. Action должен выражать смысл, например itemAdded, а не произвольное изменение DOM.
  2. Middleware находится вокруг обработки dispatch и может выполнять дополнительную логику: логирование, async-work, запуск новых actions.
  3. Reducer получает предыдущее состояние и action и рассчитывает новое состояние без сетевых запросов и других побочных эффектов. Это позволяет воспроизводить расчёт.
  4. Store уведомляет подписчиков. Selectors выбирают нужные данные, а React-компоненты показывают новое состояние. Redux Toolkit упрощает соблюдение этих правил.

Разберём на примере

Пользователь добавил товар. Action сообщает ID товара; reducer меняет корзину. Если сначала нужен запрос, async middleware может получить результат и отправить отдельные actions загрузки/успеха/ошибки. Нельзя спрятать fetch внутри reducer: его выполнение перестанет быть чистым расчётом.

Термины и элементы темы
Action
Описание события, например itemAdded. Dispatch передаёт его в поток обработки.
Reducer
Чистая функция previous state + action → next state. Redux Toolkit позволяет удобные записи через Immer при сохранении immutable результата.
Store и selectors
Store хранит состояние и подписки; selectors выбирают данные для UI.
Middleware
Перехватывает dispatch для side effects, логирования или async-логики; не помещать запросы в reducer.

Коротко по теме

Однонаправленный поток делает события и изменения прослеживаемыми. Redux полезен для достаточно сложного общего client state; для любого локального input он не обязателен.

Redux: fundamentals

RTK Query, TanStack Query, SWR и MobX

Данные с сервера отличаются от обычного UI-state. Даже если ответ уже получен, он может устареть, потребовать повторной загрузки или измениться после mutation. Библиотеки запросов берут на себя этот жизненный цикл. Redux и MobX могут моделировать клиентские данные, но это не то же назначение, что кэш server state.

Как это работает — по шагам

  1. Ключ запроса связывает результат с его параметрами: например, пользователь 7 и пользователь 8 — разные данные. Неполный ключ может привести к показу не той выборки.
  2. Кэш позволяет использовать уже полученный результат. Политика свежести определяет, когда нужен refetch; наличие кэша не означает вечную актуальность.
  3. Mutation изменяет данные. После неё можно обновить соответствующие записи кэша или инвалидировать запросы, чтобы перечитать сервер.
  4. RTK Query интегрирован с Redux Toolkit. TanStack Query и SWR используются независимо от Redux. MobX строит реактивный state на observables и computed, а не является их полным аналогом.

Разберём на примере

После изменения имени нужно обновить профиль и список участников. Можно вручную исправлять копии в нескольких компонентах, рискуя пропустить одну. Библиотека server state помогает связать эти данные с query keys и правилами обновления. Состояние открытого окна редактирования по-прежнему может оставаться локальным.

Термины и элементы темы
RTK Query
Кэш запросов и mutations в экосистеме Redux Toolkit; endpoints, tags и invalidation.
TanStack Query
Server state независимо от Redux: query keys, staleTime, retries, invalidation и mutations.
SWR
Подход к server state с кэшем и revalidation; useSWR получает key и fetcher.
MobX
Observable state, actions и computed; observer подписывает компонент на observables, прочитанные при render. Это не только библиотека сетевых запросов.

Коротко по теме

Для server state выбираю query-библиотеку с кэшем, повторными запросами и инвалидацией: RTK Query удобен в Redux-приложении, TanStack Query или SWR — при соответствующей модели проекта. Redux и MobX могут управлять сложным client state. Они не заменяют автоматически политику свежести серверных данных.
