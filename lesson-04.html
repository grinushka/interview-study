Workers и обмен сообщениями

Web Worker, SharedWorker и Service Worker

Основной поток браузера выполняет JavaScript страницы и участвует в обработке взаимодействий. Если надолго занять его расчётом, пользователь видит зависание. Workers позволяют вынести работу в другой контекст, но цена этого — отсутствие прямого доступа к DOM и необходимость явно обмениваться сообщениями.

Как это работает — по шагам

  1. Dedicated Worker получает задачу и возвращает результат сообщением. Он подходит для вычислений, которые можно выполнить без обращения к элементам страницы.
  2. SharedWorker может быть общей точкой для нескольких подходящих вкладок. Вместо отдельного экземпляра на каждую вкладку они подключаются через ports.
  3. Service Worker имеет другую роль: обработка событий сети, offline, push и обновлений. Это не постоянно работающий процесс, которому можно доверить единственную копию важных данных.
  4. Передача сообщения обычно копирует поддерживаемые данные по правилам structured clone. Некоторые buffers можно передать с передачей владения, чтобы избежать дорогой копии.

Разберём на примере

Возможные применения: Dedicated Worker обрабатывает изображение или ZIP без блокировки UI; SharedWorker централизует SSE для подходящих вкладок; Service Worker принимает Push. Это предложения, а не утверждение о выполненной работе.

// Страница
const worker = new Worker("compute.js");
worker.onmessage = ({ data }) => renderResult(data);
worker.postMessage([1, 2, 3]);
// compute.js
self.onmessage = ({ data }) => {
  self.postMessage(data.reduce((sum, n) => sum + n, 0));
};
// После работы: worker.terminate();
  1. У страницы и worker разные JS-контексты.
  2. Данные передаются structured clone, а не общей ссылкой на массив.
  3. Worker возвращает результат; DOM обновляет renderResult на странице.

Разберём на примере

SharedWorker: подключение страницы к общему worker. Сценарий учебный; обработку ошибок и выбор поддерживаемой платформы добавляет приложение.

// Страница
const shared = new SharedWorker("shared.js");
shared.port.onmessage = ({ data }) => renderResult(data);
shared.port.postMessage({ type: "hello" });
// shared.js
self.onconnect = ({ ports: [port] }) => {
  port.onmessage = ({ data }) => port.postMessage({ received: data.type });
};
  1. У SharedWorker сообщения идут через MessagePort. Назначение onmessage запускает этот port.
  2. Подходящие вкладки с одинаковым URL worker и параметрами подключаются к одному экземпляру; состояние не является постоянным storage.

Разберём на примере

Service Worker: страница регистрирует обработчик, а браузер запускает его на событие. Push подписка и серверная отправка здесь не реализованы.

// Страница, HTTPS или localhost
await navigator.serviceWorker.register("sw.js");
// sw.js
self.addEventListener("push", event => {
  event.waitUntil(self.registration.showNotification("Новое событие", {
    body: "Откройте приложение", tag: "activity"
  }));
});
  1. register создаёт регистрацию, а не вечный процесс.
  2. waitUntil связывает работу с событием, но не обещает неограниченного времени жизни.
  3. В worker нет DOM и localStorage; нужное устойчивое состояние хранится отдельно.
Термины и элементы темы
Dedicated Web Worker
Отдельная вычислительная задача: большой разбор файла, расчёты. Не ускоряет сам алгоритм автоматически, но разгружает UI.
SharedWorker
Общий worker для нескольких подходящих same-origin контекстов; соединения через MessagePort. Можно централизовать соединение, учитывая поддержку браузеров.
Service Worker
Событийный посредник для fetch, offline, push и обновлений. Нужен secure context; браузер может остановить его, поэтому память не является постоянным хранилищем.

Коротко для собеседования

Web Worker разгружает вычисления страницы; SharedWorker координирует контексты; Service Worker обслуживает события приложения и сети. Worker не делает алгоритм бесплатным и не даёт прямого доступа к UI.

Уточнение к Notion: Service Worker запускается браузером на события и может завершаться между ними. Поддержку SharedWorker и конкретных worker API проверять по compatibility table, а не по старым спискам браузеров.

BroadcastChannel

Несколько вкладок одного приложения — отдельные JavaScript-контексты. Переменная, изменённая в одной вкладке, сама по себе не меняется в другой. BroadcastChannel позволяет послать сообщение всем подходящим слушателям канала: например, сообщить о logout или об изменившейся корзине.

Как это работает — по шагам

  1. Каждая вкладка создаёт BroadcastChannel с одним и тем же именем. Совпадения имени недостаточно: действуют origin и правила storage partition.
  2. Отправитель вызывает postMessage. Другие подходящие экземпляры получают событие message и сами решают, как изменить свой UI или перечитать состояние.
  3. Сообщения не становятся постоянной историей. Если вкладки не было в момент отправки, при открытии она должна получить актуальное состояние отдельно.
  4. Когда компонент или контекст больше не нуждается в канале, обработчики снимаются и канал закрывается. В React эту пару удобно организовать через setup и cleanup эффекта.

Разберём на примере

Пользователь вышел из аккаунта в первой вкладке. Она завершает сессию и рассылает {type:"logout"}. Остальные очищают локальное представление пользователя. Третья вкладка, открытая через минуту, не получит старое сообщение: она должна проверить текущую сессию.

const channel = new BroadcastChannel("session");
channel.onmessage = ({ data }) => {
  if (data.type === "logout") showLoggedOutUI();
};
channel.postMessage({ type: "logout" });
// При завершении работы: channel.close();
  1. Одинаковое имя session объединяет подходящих участников.
  2. onmessage описывает реакцию текущей вкладки на чужие сообщения.
  3. postMessage не заменяет завершение сессии на сервере; он только уведомляет другие контексты.
Термины и элементы темы
Создание
new BroadcastChannel("auth"); каждый участник подписывается на message.
Передача
postMessage(data) использует structured clone. Объект отправителя не получает своё сообщение через тот же экземпляр; другие экземпляры могут получить.
Завершение
Убирать обработчики и вызывать close(), когда канал больше не нужен. Закрытая вкладка пропускает сообщения.

Коротко для собеседования

BroadcastChannel — локальная доставка сообщений между контекстами, а не хранилище, сетевой транспорт или гарантия однократного действия.

MDN: BroadcastChannel

Как выбрать связь между вкладками и iframe

Прежде чем выбирать API, нужно определить границу общения. Вторая вкладка того же сайта, встроенный платёжный iframe другого сайта и телефон пользователя — три разных случая. Они требуют разных возможностей доступа и не решаются одним общим каналом.

Как это работает — по шагам

  1. Для подходящих same-origin вкладок удобен BroadcastChannel. Для сохранённого состояния можно использовать хранилище и событие об изменении, но доставка и хранение остаются разными задачами.
  2. Для конкретного окна или iframe есть postMessage. Нужна ссылка на получателя: например, iframe.contentWindow. Участники могут иметь разные origins.
  3. При получении сообщения нельзя доверять только его полю type. Проверяются origin отправителя, source и структура данных; при отправке указывается ожидаемый targetOrigin.
  4. Для другого устройства или пользователя нужен сервер. Ни localStorage, ни BroadcastChannel не превращаются в сеть между компьютерами.

Разберём на примере

Смена темы в соседней вкладке подходит для BroadcastChannel. Сообщение «оплата завершена» из iframe платёжного сервиса требует postMessage с проверкой ожидаемого отправителя. Изменение документа у коллеги на другом устройстве приходит через серверный канал, например WebSocket.

Термины и элементы темы
Same-origin вкладки
BroadcastChannel для сообщений; storage event для изменений localStorage в других вкладках. Начальное состояние читать отдельно.
iframe / popup
window.postMessage при наличии ссылки на окно. Задать точный targetOrigin, проверять event.origin, source и форму данных.
Общий координатор
SharedWorker или Service Worker может пересылать сообщения; учитывать разный жизненный цикл.
Другие устройства
Локальные каналы не передают данные по сети. Нужен сервер: WebSocket, SSE или запросы.

Коротко для собеседования

Тему same-origin вкладок можно передавать через BroadcastChannel либо хранить в localStorage с обработкой storage event. Начальную тему прочитаю из storage. Результат cross-origin iframe получу через postMessage с точным targetOrigin и проверками origin, source и data.

Дедупликация уведомлений между вкладками

Три вкладки получили одно событие с ID n42. Каждая собирается показать toast. Если сначала спросить localStorage, а потом записать результат, две вкладки могут обе прочитать «ещё нет». Нужна атомарная координация решения, а не просто рассылка «я показал».

Как это работает — по шагам

  1. Назначить стабильный event ID на стороне источника. Повторная доставка того же события должна сохранять ID.
  2. Выбрать архитектуру: лидер с одним соединением или согласованная обработка в нескольких вкладках. Лидер всё равно должен учитывать replay после reconnect.
  3. Для Web Locks все участники защищают общую критическую секцию одинаковым lock, затем читают и записывают общую историю ID внутри callback. Без lock отдельные getItem/setItem дают гонку.
  4. Альтернатива: IndexedDB add с уникальным ключом event ID. Успех claim подтверждать завершением транзакции; существующий ключ означает дубль.
  5. Запись перед показом допускает пропуск при падении. Показ перед записью допускает повтор. Toast и запись истории не образуют общую транзакцию.
  6. Хранить историю ограниченное время и очищать старые ID. После TTL событие может снова считаться новым. Для нескольких устройств и бизнес-эффектов нужна серверная идемпотентность.

Разберём на примере

Учебный вариант выбирает claim перед показом и TTL 24 часа. Это политика «лучше пропустить при сбое, чем показать повторно» в пределах общей истории; ошибки storage нельзя выдавать за успешную обработку.

// Все вкладки используют одинаковый lock и ключ.
async function showOnce(event) {
  await navigator.locks.request("notification-history", async () => {
    const key = `shown:${event.id}`;
    const expires = Number(localStorage.getItem(key) || 0);
    if (expires > Date.now()) return;
    // Claim перед показом: выбираем риск пропуска, а не повтора.
    localStorage.setItem(key, String(Date.now() + 86_400_000));
    showToast(event.text); // функция интерфейса приложения
  });
}
  1. Lock общий для истории; в примере все операции с ней идут последовательно.
  2. Запись expires происходит до showToast: другая вкладка после получения lock увидит claim.
  3. Необработанный отказ localStorage или locks должен попасть в обработчик ошибки вызывающего кода. Нельзя молча считать событие показанным.
  4. TTL в примере проверяет свежесть отметки, но физическую очистку старых ключей нужно выполнять отдельно под тем же lock.

Разберём на примере

Атомарный claim через IndexedDB: store claims уже создан с уникальным ключом id. Ниже показан другой протокол координации, а не дополнительный обязательный шаг после Web Locks.

// db уже открыт; store claims создан с keyPath: "id".
function claim(db, id) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("claims", "readwrite");
    let duplicate = false;
    const request = tx.objectStore("claims").add({ id, at: Date.now() });
    request.onerror = (e) => {
      if (request.error.name === "ConstraintError") {
        duplicate = true;
        e.preventDefault(); // ожидаемый дубль не прерывает транзакцию
      }
    };
    tx.oncomplete = () => resolve(!duplicate);
    tx.onabort = () => reject(tx.error || new Error("Transaction aborted"));
  });
}
// Показывать только после commit, а не после request.onsuccess.
if (await claim(db, event.id)) showToast(event.text);
  1. Одинаковый event ID может быть вставлен только одним участником.
  2. Успех подтверждается завершением transaction.
  3. Очистка истории и сбои между commit и показом проектируются отдельно.
Термины и элементы темы
eventId
У каждого логического события должен быть стабильный ID; повторная доставка не создаёт новое событие.
Критическая секция
Захватить именованный Web Lock, внутри прочитать общую отметку, при её отсутствии обработать и записать результат. Все участники должны соблюдать протокол.
Срок хранения и сбои
Ограничить историю ID по TTL. Падение между записью и показом может потерять уведомление, а между показом и записью — дать повтор.
Гарантии
BroadcastChannel сообщает об обновлениях, но не даёт атомарный lock. Для строгих гарантий и нескольких устройств нужна серверная координация и идемпотентность.

Коротко для собеседования

Для одного показа нужны стабильный event ID, общая история и атомарный claim. Web Locks защищает проверку с записью, IndexedDB add даёт уникальный claim. Отдельно выбираю риск пропуска или повтора при падении; лидер, BroadcastChannel и notification tag сами по себе exactly-once не дают.

Уточнение к Notion: один лидер уменьшает число соединений, но не исключает повторную доставку после reconnect. tag заменяет уведомления и не обеспечивает exactly-once. TTL ограничивает окно дедупликации.

WebSocket, SSE и long polling

Обычный HTTP-запрос даёт ответ на конкретное обращение. Для чата, уведомлений и живого прогресса хочется узнавать изменения без постоянного ручного обновления. Различия транспортов становятся понятнее, если спросить: сообщения идут в обе стороны или только от сервера, и кто восстанавливает связь после сбоя?

Как это работает — по шагам

  1. WebSocket открывает двусторонний канал. После установления соединения клиент и сервер могут независимо отправлять сообщения, в том числе бинарные.
  2. SSE передаёт серверные события текстовым HTTP-потоком. EventSource умеет переподключаться, но сервер и приложение всё равно должны поддерживать нужное восстановление событий.
  3. Long polling держит запрос до появления данных или timeout. После ответа клиент отправляет следующий запрос. Между этими запросами нужно корректно сохранять позицию продолжения.
  4. Во всех вариантах полезны ID сообщений, ограничение буферов и стратегия reconnect. Сам факт живого канала не гарантирует отсутствие пропусков и дублей.

Разберём на примере

Для чата нужен обмен в обе стороны — WebSocket естественно подходит. Для прогресса серверной задачи, где браузер только слушает, SSE может быть проще. Если инфраструктура поддерживает только обычные долгие HTTP-запросы, long polling остаётся возможным компромиссом.

Термины и элементы темы
WebSocket
Двусторонний канал с текстовыми и бинарными сообщениями. Reconnect, heartbeat и восстановление пропущенных событий проектируются приложением.
SSE / EventSource
Сервер отправляет текстовый поток text/event-stream; браузерный EventSource умеет reconnect. Для возобновления сервер должен учитывать ID событий.
Long polling
Запрос ждёт новые данные или timeout, затем клиент открывает следующий. Просто поверх HTTP, но запросы и задержки требуют контроля.

Коротко для собеседования

Для чата с частым двусторонним обменом рассмотрю WebSocket. Для серверного прогресса задачи подойдёт SSE: команды можно отправлять обычным HTTP. При ограничениях инфраструктуры long polling работает поверх повторяемых HTTP-запросов. Во всех вариантах отдельно нужны auth, ошибки, cursor и восстановление пропущенных событий.

Уточнение к Notion: WebSocket поддерживает бинарные сообщения, а не только строки.

MDN: WebSockets · MDN: Server-sent events

Альтернативы Workers: какую задачу решаем

Перед выбором worker спроси: интерфейс тормозит из-за вычислений, рендера или лишних соединений? Promise и async/await сами по себе не переносят вычисление в другой поток.

Как это работает — по шагам

  1. Для тяжёлого ZIP сравни backend и Dedicated Worker. Первый требует сервера, второй сохраняет обработку в браузере, но добавляет передачу данных.
  2. Если нужны короткие вычисления на main thread, разбей их на порции. Между порциями браузер сможет обработать ввод; длительность всей задачи не обязана уменьшиться.
  3. Если дорог именно React-render, изучи state, виртуализацию и приоритеты обновлений. Эти инструменты не ускоряют сторонний синхронный алгоритм.
  4. Для общей SSE-связи используй координатора: SharedWorker либо лидера с Web Locks и BroadcastChannel. Для событий при закрытой странице нужен другой жизненный цикл.

Разберём на примере

Возможный пример из приложения: ZIP создаётся на сервере или в worker; фильтрация списка откладывается transition; вкладки делят SSE через лидера. Это три разных решения трёх разных проблем.

for (let i = 0; i < items.length; i += 100) {
  processBatch(items.slice(i, i + 100));
  if (globalThis.scheduler?.yield) await scheduler.yield();
  else await new Promise(resolve => setTimeout(resolve, 0));
}
  1. processBatch — условная функция приложения; каждая порция тоже должна быть короткой.
  2. yield отдаёт управление браузеру; await Promise.resolve() этого не заменяет, потому что добавляет microtask.
  3. Уступка потока улучшает отзывчивость, но не создаёт параллельное вычисление.
Термины и элементы темы
Backend
ZIP, PDF или конвертацию можно вынести на сервер: меньше CPU на устройстве, но нужны сеть, передача данных и серверные ресурсы.
Разбиение вычислений
Делить цикл на небольшие части и уступать main thread через scheduler.yield с проверкой поддержки или setTimeout. Общая работа остаётся в UI-потоке.
Нативные API
createImageBitmap, OffscreenCanvas и асинхронные методы могут помочь конкретной операции. async в названии не гарантирует отсутствие всей работы на main thread.
React concurrency
useTransition и useDeferredValue управляют приоритетами React-render. Произвольный синхронный ZIP-код они не переносят в другой поток.
Общая связь вкладок
Web Locks выбирает вкладку-лидера, BroadcastChannel передаёт сообщения. Это альтернатива SharedWorker для подходящих контекстов, а не фоновый сервер.
Частичная замена Service Worker
HTTP-кэш ускоряет загрузку онлайн; IndexedDB хранит данные, но не гарантирует загрузку app shell offline. Web Push требует Service Worker.

Коротко для собеседования

ZIP: backend или Dedicated Worker. Тяжёлый список: сначала измерение React-render, затем организация state и подходящая оптимизация. Общий SSE: координатор вкладок. Выбор зависит от места выполнения и жизненного цикла, а не от слова async.

Уточнение к Notion: обещание «около 20 строк» не учитывает reconnect, восстановление данных, завершение и ошибки. Поддержку API проверять для целевых браузеров.

Web Locks: критическая секция и вкладка-лидер

Три вкладки не должны открывать три одинаковых SSE-соединения. Одна становится лидером, другие получают её сообщения. Lock координирует владение, BroadcastChannel — доставку внутри браузера.

Как это работает — по шагам

  1. Каждая вкладка запрашивает один exclusive lock с одинаковым именем. Только один callback начнёт работу.
  2. Лидер создаёт EventSource и обновляет свой UI сам; сообщения другим вкладкам пересылает в BroadcastChannel.
  3. Callback остаётся pending, пока соединение нужно. finally закрывает EventSource при контролируемом завершении.
  4. После закрытия лидера другой участник может получить lock. Он заново подключается и восстанавливает данные по серверному cursor или snapshot.

Разберём на примере

Код показывает протокол владения, но updateUI, формат событий и серверное восстановление принадлежат приложению. stop.abort отменяет ожидание; для владельца дополнительно предусмотрен собственный обработчик abort.

const bus = new BroadcastChannel("events");
bus.onmessage = ({ data }) => updateUI(data);
const stop = new AbortController();
// Каждая вкладка вызывает этот код; одна получит exclusive lock.
navigator.locks.request("sse-leader", { signal: stop.signal }, async () => {
  if (stop.signal.aborted) return;
  const source = new EventSource("/events");
  source.onmessage = ({ data }) => {
    updateUI(data); // свой BroadcastChannel сообщение не получит
    bus.postMessage(data);
  };
  try {
    await new Promise(resolve => {
      stop.signal.addEventListener("abort", resolve, { once: true });
    });
  } finally { source.close(); }
}).catch(error => {
  if (error.name !== "AbortError") console.error(error);
});
// При явном завершении: stop.abort(); bus.close();
  1. Имя sse-leader должно совпадать во всех вкладках.
  2. Promise удерживает callback незавершённым; событие abort позволяет завершить его явно.
  3. Для production нужны начальный snapshot, обработка auth, storage partition и механизм replay после смены лидера.
Термины и элементы темы
Время удержания
Lock удерживается до завершения callback или возвращённого им Promise. Длительная async-операция должна быть await внутри callback.
Очередь и режимы
exclusive допускает одного владельца; shared допускает нескольких читателей. Очередь ожидающих не является гарантией своевременной работы фоновой вкладки.
ifAvailable
Без ожидания вызывает callback с lock или null. Получение null нужно обработать, оно не означает успешный захват.
Отмена ожидания
signal отменяет ожидающий запрос. Уже выданный lock он сам не освобождает: callback должен закончиться через собственный сигнал завершения.
Выбор лидера
Одна вкладка держит соединение внутри callback, остальные ждут. После освобождения lock другой участник может стать лидером.
Ошибки и диагностика
Обрабатывать rejection request, освобождать ресурсы в finally; query показывает held/pending. steal — исключительный механизм, не откатывающий чужие побочные эффекты.

Коротко для собеседования

Web Locks даёт одного владельца критической секции среди согласованных участников. Для общего SSE держу lock на время соединения, рассылаю события и отдельно проектирую восстановление. Закрытие вкладки освобождает lock, но не восстанавливает данные.

Уточнение к Notion: освобождение lock при закрытии вкладки не даёт бесшовный failover. Возможны пауза, потерянные события и throttling. Lock не делает действия ровно однократными.

postMessage: доверие к отправителю и данным

В страницу встроен виджет другого origin. Он просит изменить размер iframe. Родитель должен разрешать только предусмотренную команду от конкретного виджета.

Как это работает — по шагам

  1. Сначала проверить event.origin точным сравнением, а затем event.source — относительно нужного iframe.
  2. Проверить, что data — объект известного типа сообщения. Ограничить числовые поля разумным диапазоном.
  3. Выполнить только разрешённое действие. Не интерпретировать вход как HTML или JavaScript.
  4. При ответе указать точный targetOrigin; навигация iframe не должна превратить его в получателя секрета.

Разберём на примере

В примере допустима только команда resize с высотой от 100 до 1200. Даже другое окно с тем же origin будет отклонено проверкой source.

const frame = document.querySelector("iframe");
const trusted = "https://widget.example";
window.addEventListener("message", (event) => {
  if (event.origin !== trusted) return;
  if (event.source !== frame.contentWindow) return;
  const data = event.data;
  if (!data || typeof data !== "object") return;
  if (data.type !== "resize" || !Number.isFinite(data.height)) return;
  if (data.height < 100 || data.height > 1200) return;
  frame.style.height = `${data.height}px`;
});
frame.addEventListener("load", () => {
  frame.contentWindow.postMessage({ type: "init" }, trusted);
});
  1. origin проверяет сайт отправителя, source — конкретное окно.
  2. Number.isFinite отвергает строки, NaN и Infinity; диапазон ограничивает эффект команды.
  3. Секреты не передаются через wildcard targetOrigin; пример работает с обычным origin iframe, не opaque sandbox.
Термины и элементы темы
targetOrigin
При отправке задавать точный origin получателя. Звёздочка может раскрыть сообщение после навигации окна на другой сайт.
event.origin
Сравнивать со строгим allowlist полных origins. includes и startsWith не подходят для проверки доверенного домена.
event.source
Проверять ссылку на ожидаемое окно, например iframe.contentWindow. Это различает несколько iframe одного origin.
event.data
Проверять тип сообщения, поля и допустимые значения. Не вставлять произвольные данные в innerHTML, eval или URL перехода.
Права на действие
Валидная форма сообщения не даёт разрешения на оплату или удаление. Проверять допустимость операции в протоколе и права на сервере.

Коротко для собеседования

Проверяю origin, конкретное окно source, структуру и смысл data. Отправляю с точным targetOrigin. После этого выполняю только разрешённую команду; права на бизнес-операции всё равно проверяет сервер.

storage event: кому приходит изменение

Документ — отдельная загруженная страница: iframe тоже документ. Общая область хранения и документ-писатель — разные понятия.

Как это работает — по шагам

  1. A и B открыты на https://app.example, внутри A есть iframe этого origin. A меняет значение localStorage.
  2. B и iframe получают событие, A — нет. Другой origin его не получает. Внешние embedding-контексты могут иметь отдельную storage partition.
  3. При sessionStorage B исключается: область ограничена вкладкой A, но same-origin iframe внутри неё может получить событие.
  4. На старте прочитать getItem. При повторной записи того же значения нового события нет. Обновление UI писателя выполняется напрямую.

Разберём на примере

Для темы нужен снимок при загрузке и обработчик дальнейших изменений. Нельзя ждать первого storage event, чтобы узнать сохранённую тему.

const key = "theme";
applyTheme(localStorage.getItem(key) || "light");
window.addEventListener("storage", event => {
  if (event.storageArea === localStorage && (event.key === key || event.key === null)) {
    applyTheme(localStorage.getItem(key) || "light");
  }
});
function changeTheme(theme) {
  localStorage.setItem(key, theme);
  applyTheme(theme); // писатель своего события не получает
}
  1. applyTheme — функция интерфейса приложения.
  2. key=null учитывает clear, который удаляет и тему.
  3. Схема: A → localStorage → B и iframe; обратной стрелки события к A нет.
Термины и элементы темы
localStorage
Другие вкладки и окна того же origin с общей областью хранения, включая подходящие same-origin iframe.
sessionStorage
Другие same-origin документы внутри той же вкладки, обычно iframe. Другая вкладка имеет другую область sessionStorage.
Изменение значения
setItem с прежним значением не создаёт изменение. Начальное состояние читать отдельно: storage event не является историей.
Поля события
key, oldValue, newValue, storageArea и url. removeItem даёт newValue=null; clear даёт key=null.
Синхронизация UI
Писатель обновляет свой UI сам. Получатели фильтруют key и перечитывают или применяют новое значение.

Коротко для собеседования

storage приходит другим документам с общей областью хранения. localStorage обычно связывает same-origin вкладки; sessionStorage — документы внутри одной вкладки. Писатель не получает событие, начальное состояние и свой UI обновляет отдельно.

Same-origin iframe: зачем и где граница изоляции

В новом интерфейсе можно временно показывать legacy-экран в iframe. Его стили не смешиваются с родительскими, но доверие к коду определяется origin и sandbox.

Как это работает — по шагам

  1. Для доверенного legacy same-origin iframe позволяет интеграцию и отдельный жизненный цикл страницы.
  2. Для печати отдельный документ задаёт собственные размеры и стили; после загрузки вызывается его print.
  3. Для пользовательского HTML сначала нужна граница безопасности: отдельный origin и минимальные разрешения sandbox.
  4. Общение через postMessage требует проверки origin/source/data. Opaque origin sandbox требует отдельной модели протокола и доверия.

Разберём на примере

Trusted legacy и пользовательский HTML внешне могут выглядеть одинаково, но нельзя выдавать им одинаковые разрешения.

Термины и элементы темы
Виджеты и legacy
Встроить старую страницу или независимый редактор со своим CSS и глобальными переменными.
Предпросмотр и печать
Рендерить шаблон или печатный layout без изменения основного документа.
Same-origin доступ
Родитель может обращаться к contentWindow и DOM при отсутствии ограничений sandbox. Общий origin допускает общий storage, но JS-память каждого документа отдельная.
sandbox
Без allow-same-origin документ получает opaque origin. Сочетание allow-scripts и allow-same-origin для недоверенного same-origin содержимого может разрушить изоляцию.
Недоверенный HTML
Использовать отдельный origin, подходящий sandbox и узкий протокол postMessage. Изоляция CSS сама по себе не защищает от вредоносного JavaScript.

Коротко для собеседования

Iframe полезен для отдельного документа: legacy, редактор, печать. Same-origin упрощает доступ, но не изолирует недоверенный код. Для него выбираю отдельный origin, минимальный sandbox и проверенный протокол сообщений.

Уточнение к Notion: скрытый iframe принадлежит конкретной странице и сам по себе не создаёт одно общее соединение для независимых вкладок.

Notifications и Push: показ и доставка

Пользователь хочет получать уведомления о сообщениях. Отдельно решаем доставку события, разрешение и показ. Тренажёр изучает API, но сам не просит доступ и не подключает Push.

Как это работает — по шагам

  1. Кнопка «Включить уведомления» объясняет цель. После нажатия проверить API и запросить разрешение.
  2. Для события при открытой странице возможен обычный UI-toast. Системное уведомление требует разрешения.
  3. Для Web Push нужна серверная подписка и Service Worker. Он запускается на событие, а не работает постоянно.
  4. В обработчике клика закрыть notification, найти подходящий клиент или открыть известный разрешённый URL. Не доверять произвольному URL из внешних данных.

Разберём на примере

Учебный фрагмент: Service Worker уже зарегистрирован приложением; после разрешения показывается persistent notification. Это демонстрация API, не рабочая Push-подписка.

button.addEventListener("click", async () => {
  if (!("Notification" in window) || !("serviceWorker" in navigator)) return;
  const permission = await Notification.requestPermission();
  if (permission !== "granted") return;
  const registration = await navigator.serviceWorker.ready;
  await registration.showNotification("Новое сообщение", {
    body: "Откройте приложение", tag: "chat-42", data: { path: "/messages/42" }
  });
});
  1. ready ожидает активную регистрацию: без заранее зарегистрированного Service Worker пример не завершит ожидание.
  2. tag выбирает группу показанных уведомлений; историю event ID хранить отдельно.
  3. Обработчик notificationclick находится в файле Service Worker, а не в странице.

Разберём на примере

Обработчик клика находится в Service Worker. Пример открывает заранее известный маршрут; для фокусировки существующего окна можно добавить clients.matchAll.

self.addEventListener("notificationclick", event => {
  event.notification.close();
  event.waitUntil(clients.openWindow("/messages"));
});
  1. Не передаём произвольный внешний URL из payload напрямую в openWindow.
  2. event.waitUntil позволяет браузеру учитывать async-работу обработчика.
Термины и элементы темы
Разрешение
permission: default, granted или denied. Запрашивать по понятному действию пользователя в secure context. Отказ нельзя обходить повторным показом запроса.
Показ уведомления
new Notification привязан к странице; для мобильных браузеров использовать persistent notification через registration.showNotification и проверять поддержку.
Push
Нужны Service Worker, push subscription и серверная отправка. Подписка и право на показ — связанные, но разные части механизма.
tag и оформление
body/icon/data описывают содержимое; tag группирует или заменяет подходящие уведомления. Поддержка actions, image и других опций различается.
Клик и видимые клиенты
В Service Worker обработать notificationclick, закрыть уведомление и открыть или сфокусировать разрешённый URL. clients.matchAll помогает найти подходящие окна.

Коротко для собеседования

Notifications отвечает за показ, Push — за доставку к Service Worker. Разрешение запрашиваю после действия пользователя; на мобильных ориентируюсь на showNotification. Для закрытой страницы нужны подписка и сервер, а tag не заменяет дедупликацию событий.

Уточнение к Notion: tag заменяет уведомления по правилам API и не является гарантией «ровно один раз». На iOS Web Push связан с web app на Home Screen; поддержка и настройки ОС требуют отдельной проверки.
