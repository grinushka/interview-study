React: рендеринг

Render, commit и жизненный цикл

В React вызов функции компонента и изменение экрана — не одно событие. Функция сначала вычисляет, каким UI должен быть при текущих props и state. После согласования результата React применяет необходимые изменения. Разделение помогает понять, почему render должен быть чистым и почему эффекты нельзя произвольно запускать внутри него.

Как это работает — по шагам

  1. Обновление state ставит работу в очередь. Оно не обязано немедленно изменить DOM в следующей строке обработчика.
  2. Во время render React вызывает компоненты и получает описание элементов. Здесь рассчитываются значения; нельзя считать каждый вызов гарантированным «показом» пользователю.
  3. React сопоставляет новое дерево с предыдущим. Если нужный DOM уже соответствует результату, повторный render может не потребовать видимого изменения.
  4. На commit применяются изменения. С этим этапом связаны refs и layout effects; обычные effects синхронизируют внешние системы после соответствующего commit по своим правилам.

Разберём на примере

Компонент вернул ту же надпись "Сохранено" после обновления родителя. Функция могла вызваться снова, но браузерному текстовому узлу не требуется становиться другим. Если же внутри render отправлялась аналитика, одно вычисление UI могло бы ошибочно считаться ещё одним просмотром.

Термины и элементы темы
Trigger
Первый mount или update state; обновление родителя обычно инициирует render дочернего дерева.
Render
React вызывает компоненты и сравнивает результат с предыдущим деревом. Повторный render не обязательно означает изменение DOM.
Commit
React применяет нужные DOM-изменения и обновляет refs; layout effects привязаны к commit.
Mount / update / unmount
У class есть componentDidMount/DidUpdate/WillUnmount. У функций эффекты описывают отдельные процессы синхронизации с cleanup, а не точную замену каждого class lifecycle.

Коротко по теме

Render — расчёт описания UI; commit — применение результата. React может повторить расчёт, поэтому побочные эффекты должны иметь подходящее место и жизненный цикл.

Virtual DOM, reconciliation и keys

State принадлежит не строке кода и не объекту из массива, а конкретному месту компонента в React-дереве. При изменении списка React должен понять, какие элементы сохранились, какие исчезли и какие появились. Key помогает сопоставить элементы среди соседей и сохранить состояние за правильной сущностью.

Как это работает — по шагам

  1. React получает новое описание UI и сравнивает его с предыдущим. Virtual DOM — распространённое название этой модели описания в памяти, а не полный дубль браузерной страницы.
  2. В списке стабильный key из данных позволяет узнать прежний элемент после перемещения. Он должен быть уникален среди siblings, а не обязательно во всём приложении.
  3. Индекс описывает позицию, а не сущность. После вставки в начало key=0 относится уже к другому товару, хотя прежний компонент на позиции 0 мог сохранить state.
  4. Случайный key меняется при каждом render. React видит новую идентичность и может пересоздать компонент с потерей локального состояния.

Разберём на примере

В первой строке списка пользователь набрал черновик. Затем список отсортировали. С key по ID черновик остаётся у той же записи. С key по индексу он может оказаться у другой записи на прежней позиции: React сохраняет экземпляр по ключу, а не по твоему намерению.

Термины и элементы темы
Virtual DOM
Условное имя описания UI в памяти; не копия всего браузерного DOM и не гарантия большей скорости для любого интерфейса.
Reconciliation
Сопоставить старое и новое дерево, сохранить подходящие instances/state и определить изменения.
Keys
Стабильный ключ из данных помогает сохранять state за правильным элементом. Индекс при перестановках и случайный key могут привязать state неверно или перемонтировать элемент.

Коротко по теме

Key — часть идентичности элемента среди соседей. Стабильный ID сохраняет связь UI-state с данными при перестановках; индекс и random key часто эту связь нарушают.

Fiber и concurrent rendering

Если React долго обрабатывает большое дерево без возможности уступить управление, ввод и другие срочные действия могут ждать. Fiber организует render как набор единиц работы с приоритетами. Это основа для конкурентного рендеринга, в котором менее срочную работу можно прервать ради более важной.

Как это работает — по шагам

  1. React хранит внутреннее представление работы и связи между частями дерева. Оно помогает продолжать обработку, а не только проходить всё дерево одним вложенным синхронным вызовом.
  2. Обновления могут иметь разный приоритет. Ввод в поле должен быстро показать символ; пересчёт тяжёлого списка по этому вводу может быть менее срочным.
  3. React может уступить управление, прервать render и начать работу с более актуальными данными. Поэтому промежуточный render не гарантирует commit.
  4. Commit применяет согласованный результат. Конкурентность здесь не означает, что функции компонентов автоматически считают UI в нескольких CPU-потоках.

Разберём на примере

При вводе поискового запроса буква появляется сразу, а тяжёлый список обновляется как transition. Если пользователь быстро допечатал ещё букву, React может не доводить старый промежуточный render списка до экрана. Но слишком дорогую неделимую функцию внутри компонента всё равно нужно оптимизировать.

Термины и элементы темы
Stack reconciler
Длинная синхронная обработка дерева затрудняла уступку управления браузеру.
Fiber nodes
Единицы работы связаны с компонентами и хранят сведения о state, props и связях дерева; детали реализации не являются публичным API.
Приоритеты
Urgent ввод и transition-обновление могут иметь разные приоритеты. Это не параллельное выполнение render в нескольких JS-потоках.
Практическое следствие
Чистые render, корректные эффекты и useTransition/useDeferredValue помогают сохранять отзывчивость.

Коротко по теме

Fiber даёт модель управляемой работы и приоритетов. Concurrent rendering помогает отзывчивости, но не отменяет стоимость вычислений и требования к чистоте render.

Уточнение к Notion: «Fiber 2.0» — не отдельная официальная версия публичного API; внутренние поля и алгоритмы могут меняться.
