Рендеринг и SEO

CSR, SSR, SSG, ISR и hybrid

Чтобы показать страницу, браузеру нужен HTML и связанная работа приложения. Rendering strategy определяет, где и когда формируется начальное содержимое: при сборке, при запросе на сервере или уже в браузере. От этого зависят стартовый контент, свежесть данных, серверная стоимость и кэширование.

Как это работает — по шагам

  1. При CSR браузер получает основу и строит основной UI после загрузки JavaScript. Это удобно для интерактивного приложения, но стартовый путь зависит от доступности и выполнения JS.
  2. При SSR сервер формирует HTML для запроса. Пользователь может раньше увидеть содержимое, но генерация и данные требуют времени на сервере; интерактивность часто приходит позже с hydration.
  3. При SSG HTML подготовлен заранее. Ответ легко кэшировать, но изменения исходных данных не попадают в старый результат автоматически.
  4. ISR обновляет заранее подготовленный результат по правилам framework. Hybrid означает, что разные маршруты или части используют разные стратегии по своим требованиям.

Разберём на примере

Статью с редкими изменениями удобно подготовить заранее. Персональный кабинет не должен отдавать всем один общий HTML с чужими данными. Каталог может сочетать кэшируемые публичные страницы и динамические персональные элементы. Выбор «SSR для всего» не снимает эти различия.

Термины и элементы темы
CSR
Основной UI строится в браузере после JS. Подходит для интерактивных закрытых приложений; учитывать стартовую загрузку.
SSR
HTML формируется для запроса на сервере; помогает первому контенту, но добавляет серверную стоимость и требует продуманного кеширования.
SSG
HTML формируется заранее при сборке; хорошо кэшируется, но обновление данных требует обновления результата.
ISR
Предварительный результат обновляется позже по времени или invalidation, поведение зависит от framework.
Hybrid / dynamic
Разные маршруты/части используют разные стратегии. Dynamic rendering в framework-контексте — генерация на запрос; независимые fetch можно запускать параллельно, а не создавать waterfall.

Коротко для собеседования

Выбор зависит от свежести, персонализации, стартового контента и стоимости. Серверный HTML и готовность к взаимодействию — отдельные этапы.

Hydration, streaming и universal app

При SSR пользователь может уже видеть HTML до загрузки клиентского React. Hydration позволяет React принять этот HTML как начальное отображение и подключить свою модель приложения. Для этого клиентское описание должно соответствовать серверному: нельзя без последствий начать с другой страницы под теми же DOM-узлами.

Как это работает — по шагам

  1. Сервер вычисляет HTML и отправляет его браузеру. Браузер может показать текст ещё до готовности приложения к обработке взаимодействий.
  2. Клиент загружает код и начинает hydration через соответствующий API. React связывает своё дерево с существующим содержимым и обработчиками.
  3. Если первый client render отличается, возникает mismatch. Причиной могут быть случайные значения, время, locale или обращение к browser-only данным.
  4. Streaming позволяет отдавать части ответа постепенно. Server Components определяют место выполнения компонентов и передачу результата; это не просто другое название hydration.

Разберём на примере

Сервер вывел Date.now(), а через секунду клиент при первом render вычислил другое число. Текст уже не совпадает. Решение зависит от задачи: передать согласованное начальное значение или отложить клиентскую часть с понятным fallback, а не просто подавить все предупреждения.

Термины и элементы темы
Совпадение
Первый client render должен соответствовать серверному: Date.now, случайные числа, locale и browser-only данные могут создать mismatch.
Streaming
Сервер может отдавать HTML частями, а Suspense обозначает границы ожидания. Это не то же самое, что fetch-stream в браузере.
Universal / isomorphic
Часть кода может работать и на сервере, и в браузере; window/document на сервере недоступны.
Server Components
Компоненты выполняются в серверной среде и не отправляют свой исполняемый код клиенту. Это отдельная модель, сочетаемая с SSR и client components.

Коротко для собеседования

Hydration делает серверный HTML частью клиентского React-приложения. Первое содержимое должно быть согласовано; window и DOM недоступны при обычном серверном выполнении.

SEO: доступность содержания поисковику

Поисковику сначала нужно найти адрес, получить страницу и понять её содержимое. Только затем можно говорить об индексации и ранжировании. Технический SEO помогает не мешать этим этапам: важный текст доступен, URL согласованы, ссылки работают, а ограничения не противоречат намерению владельца.

Как это работает — по шагам

  1. Ссылки и sitemap помогают обнаружить URL. Если до товара можно добраться только через сложную последовательность действий в JS, путь обнаружения стоит проверить.
  2. Содержимое должно быть понятно: title, headings, семантическая структура, текст и описания изображений отражают смысл страницы.
  3. robots.txt управляет crawling. noindex сообщает об исключении из индекса, но поисковик должен получить соответствующее указание. Это не взаимозаменяемые переключатели.
  4. Canonical помогает обозначить предпочтительную версию дублирующихся URL. SSR/SSG может упростить получение контента, но качество и полезность страницы остаются отдельными вопросами.

Разберём на примере

Один товар доступен по URL с разными параметрами сортировки и tracking. Поисковик может видеть множество похожих страниц. Нужно разобраться с нормальными ссылками и канонической версией, а не только добавить description. Open Graph улучшает социальный preview, но не заменяет эту работу.

Термины и элементы темы
Процесс
Crawling → обработка/rendering при необходимости → indexing → ranking; отдельные стадии могут повторяться.
Структура
Semantic HTML, понятные headings, title, description, доступные ссылки и alt. viewport относится к отображению на устройствах.
Управление URL
robots.txt управляет crawling, не надёжным удалением из индекса; noindex управляет indexing; canonical — сигнал предпочтительного URL, sitemap помогает discovery.
Дополнения
Structured data описывает сущности; Open Graph задаёт social preview; скорость и доступность полезны пользователям и поиску.

Коротко для собеседования

SEO связывает обнаружение, доступность и понимание содержимого с управлением URL. Мета-теги и SSR — части решения, а не гарантия позиции в поиске.
